# Issues and ambiguities in the `research-public-v0.1.0` task package

Found while running the 14 capability cards through Eidos (hosted Linux CPU; see `research-cards.md`). The release was not patched;
`research/public/` is unchanged. Severity is for Eidos integration, not for the release's stated development scope.

| # | Where | Observation | Evidence | Impact |
|---|---|---|---|---|
| 1 | D08, D13 cards; `instrument.py` | No executable reference path for the instrument cards. `instrument.py` is a library function (`error_slices(x, y, p, kind)`) with no CLI; its inputs (validation features, labels and predictions) are not part of any card or bundle, and `qualify.py` is the only caller. D08/D13 ("same instrument code on image and series tasks") therefore cannot be integrated without writing a wrapper that imports `data.py` (public labels). | `grep -n "error_slices" research/public/development/*.py` → only `instrument.py` and `qualify.py`; README says D08 is an authored reference, not autonomous creation. | Builder wrapper needed (`scripts/research/adapters/instrument_adapter.py`); an autonomous run of D08/D13 has no restricted bundle (only D01/D02/D12 export). |
| 2 | Cards' `qualification_receipt`, `qualification/results.json` | Qualification numbers are macOS arm64 values and no tolerance is declared for reproducing them elsewhere. On hosted Linux (torch 2.15.0+cpu) classification scores are identical, but 5 of 27 regression rows differ. | conditioning seed 11 candidate RMSE 0.5067705895416678 (macOS) vs 0.5067705427791459 (Linux); seed 23 0.8219767863889431 vs 0.8219769988398633; forecast seed 11 0.022705006698637967 vs 0.022705004770421713. Bars (0.5/0.5 gain) are unaffected. | Exact-equality regression tests against the recorded numbers would fail on Linux for regression cards; use the bar, not the number. Linux profile is unqualified by the release itself. |
| 3 | `requirements.lock` | Pins `torch==2.15.0`; on Linux the available wheel is `2.15.0+cpu` (local wheelhouse). The lock is an installed-version snapshot, not a hash lock (README says so). | `pip list` in the dev env; `docs/dev-runs/research-public-v0.1.0.md`. | Environment digest differs from the release's by construction; already documented. |
| 4 | `fresh_check.py` | Only verifies the **test** split predictions of a `project.py` artifact (needs `project.py`, `data.py` in the import path). It is not usable on restricted bundles or on candidate-authored models, and its pass condition is exact array equality, which holds only for the same-environment reload. | `fresh_check.py` loads `dataset(c['name'])` test split and asserts `np.array_equal`. | Bundles use their own fresh-process check (`check_bundles.py`); the card-level `fresh_check.py` is reference-only. |
| 5 | D11 text vs `lifecycle.py` | "Exit worker with code 17 after checkpoint, start new worker" does not say how a harness should treat the non-zero exit of a job whose checkpoint was committed before `os._exit(17)`. The committed-step notion is "file replaced via `os.replace`, then exit"; nothing states that a recovery policy may read it. | `lifecycle.py` `worker()`: `os.replace(tmp, output)` then `os._exit(17)`. | A runner that discards outputs of failed jobs (as `eidos.project.command` does) loses the committed checkpoint; recovery semantics must be specified by the harness. |
| 6 | Importing release modules from the source tree | Running `qualify.py`/`check_*.py` from `research/public/development` writes `__pycache__` into the immutable tree unless `PYTHONDONTWRITEBYTECODE=1` is set. The runs here used `PYTHONDONTWRITEBYTECODE=1` for all driver subprocesses; a `__pycache__` directory already existed in the imported tree (untracked, ignored by git, absent from `PUBLIC_MANIFEST.json`). | `ls research/public/development` shows `__pycache__` before any run of this task. | Minor: the README commands do not mention bytecode suppression; a manifest check that lists directory contents would flag it. |
| 7 | `TASK_INTERFACE.md` command examples | Reference commands take `--out DIR` and write `model.pt`, `{train,validation,test}_predictions.npz`, `receipt.json`; the interface does not name these artifact filenames as part of the contract (only `predictions.npz` in the card JSON `artifact_contract`: "project.py + model.pt + inference recipe + predictions.npz + common answer JSON"). | The reference writes `test_predictions.npz`, not `predictions.npz`. | Adapters must map filenames explicitly; harmless but ambiguous. |
