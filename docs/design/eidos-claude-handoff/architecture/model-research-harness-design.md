## Deployment and ownership

A researcher brings a PyTorch project, a question about a capability, and a budget. The lab should return the strongest answer the evidence supports, a model they can load if one improved, and a recipe another researcher can challenge. “This architecture cannot represent the distinction” and “this one learned it but its readout hid it” lead to very different experiments.

**Final architecture baseline · local v1 · Revision 4 · 7 November 2026.** Build the complete harness for a researcher to install and use on their own machine. Its internal LLM runs bounded decision turns; durable coordination and scientific records outlive those turns. Components remain replaceable, checkpoint changes create explicit branches, and assessment checks actual execution and isolation against the frozen plan. CLI, MCP and generated HTML reports are the v1 interfaces. This is the implementation baseline, with release acceptance criteria rather than milestone-sized products. The hosted cloud agent session is where we may build the software; it is not a runtime requirement for its users.

All nine architecture diagrams can be enlarged in this document or downloaded as [standalone SVG files](model-research-harness-diagrams.zip). The [local v1 topology](model-research-harness-architecture.svg) and [editable specification](model-research-harness-design.md) are also available separately.

[[topology]]

**Architecture decision.** Build a Python application with an explicit domain core, one command service, independently supervised workers and a small worker SDK. Use local PostgreSQL for research records and accounting, a content-addressed local artifact directory, Temporal for durable coordination, and per-project environments for ordinary PyTorch code. The command API, resolver, catalog and authorized evidence reader ship together. The investigator, training runner, assessor and sealed evaluation runner are separate entry points with separate credentials. Security isolation is an additional, measured property of the selected execution profile. A local supervisor owns startup, health, persistence, logs and recovery. No cloud account, OCI registry, MinIO, Kubernetes or Kueue is required for local v1.

| Owner | Decisions and durable responsibility |
|---|---|
| Researcher / project | Defines intended behavior, validity of interventions, accessible data and the pre-exploration charter. Authorizes qualified releases; cannot waive mandatory template/assessor controls. Charter amendments retain their exposure history. |
| Investigator | Maintains competing explanations, requests observations, writes candidate methods, and recommends the next experiment. Each proposal has a prediction and a condition that would count against it. |
| Command service + resolver | Authenticates each operator, enforces revision and budget rules, resolves an immutable execution plan, and accepts results through a single logical commit path. A plan can be inspected before execution. |
| Workflow and compute controllers | Temporal coordinates bounded turns and waits for durable job handles. The local compute supervisor owns process submission, device reservations and reconciliation. Scientific priority and the decision to prune belong to the study policy. Remote cluster admission is an optional backend concern. |
| Evidence service | Stores what was observed and how it was measured. It relates each claim to supporting or conflicting evidence. Access to sealed predictions, labels and restricted data is checked on every read. |
| Evidence planner | Expands a qualified protocol template into a plan that inherits the charter's success rules. Submits drafts through the command service. Records assumptions, alternatives, tuning, analysis, budget and disclosures without selecting a new success bar. |
| Protocol assessor | Checks a frozen plan against realized execution and evidence, issues an attributed assessment, and identifies incomplete obligations. Uses project-approved assessment code and independent access. It cannot silently broaden a claim's scope. |

In this design a **trial** is one controlled test, an **attempt** is one execution of that test, and a **checkpoint** is a saved model or training state. A **turn** is one bounded opportunity for the investigator to inspect evidence and choose actions. A **release** identifies immutable component code and its contract. A project environment lock describes dependencies; it does not make the code secure. The diagrams use these names consistently.

**One logical write path.** Planners submit drafts, assessors submit results, and workers submit output manifests to the command service's authenticated command/commit API. They have no direct ledger write credentials. The service checks identity, expected revision, command uniqueness, policy and applicable attempt fencing before atomically committing records and outbox events. Read services use authorized projections. Uploading immutable bytes to a staging prefix is separate from publishing authoritative artifact/evidence records. Neither a planner nor an assessor can bypass this boundary by being an internal service.

The default lab runs CPU work or uses the researcher's available accelerators through a capability-reporting local adapter. A single machine can complete the entire investigation, including independently authorized assessment. Plans requiring sealed execution use a qualified local Linux sandbox or local Linux VM profile. An unavailable device, isolation capability or exact-resume guarantee is reported before dispatch. Remote Linux GPUs and distributed backends remain compatible extensions; the local acceptance journey does not depend on renting a server.

## Local product and technology stack

**The finished user journey.** Install the lab, run `lab init` and `lab doctor`, register an existing project and interpreter, choose a local or hosted model endpoint, and start the supervisor. The researcher commits a study charter and launches an investigation through the CLI or MCP. The internal investigator can reproduce a failure, install a new diagnostic, generate data, change a learning rule, branch a checkpoint and propose a structure. The researcher can inspect receipts and plots, steer the investigation, take over, or disconnect while admitted work continues. They finish with a loadable model when justified, a reproducible recipe, and a report that includes negative results and limitations. They can reuse their new component on another project without rebuilding the lab.

CLI names here are proposed product commands, not installed commands in this workspace. `lab status --json`, `lab logs`, `lab report`, `lab component validate/publish/bind`, `lab checkpoint branch`, `lab backup` and `lab restore` are required surfaces. `lab stop` has an explicit running-job policy: drain, checkpoint-and-stop where supported, or cancel. Closing an MCP client only detaches that client. A terminal UI may later consume the same queries; neither Textual nor a browser application is required to operate v1. HTML reports supply plots, comparisons, lineage and linked evidence that are awkward to read in a terminal.

| Layer | Selected implementation | Boundary we own |
|---|---|---|
| Domain and commands | Python; standard-library domain types; Pydantic v2 at server API/configuration boundaries | Charter, component, plan, claim, branch, budget and publication rules; independent of transport or agent framework |
| API and MCP | FastAPI/ASGI and the official MCP Python SDK behind versioned transport adapters | One application command/query interface, scoped authentication, stable receipts and tested client compatibility |
| Research persistence | PostgreSQL, SQLAlchemy 2 and Alembic | Transactions, append-only scientific revisions, outbox, grants and explicit migration policy |
| Durable coordination | Temporal Python SDK and a managed local Temporal Server | Investigation coordinator, bounded turn workflows, durable job identities, retry and reconciliation policy |
| Investigator | Pydantic AI behind our `InvestigatorRuntime` port, qualified against the actual providers and failure cases | Context policy, accepted decisions, command identity, budgets and evidence permissions remain ours |
| Artifacts | Local filesystem backend with hashed immutable blobs and transactional publication manifests | Staging, integrity, retention, authorized access and backup consistency; S3-compatible storage remains an adapter |
| Project execution | Existing Python/PyTorch environment, or independently locked uv project; subprocess protocol and optional trainer hooks | Thin model adapter, declared capabilities, checkpoint state, scientific receipts and private branch state |
| Process and security profiles | Supervisor with OS process management; Linux bubblewrap profile; local Linux VM profile on macOS using Lima | Exact configuration, credential boundaries, qualification probes and realized isolation receipts |
| Operator surface | Typer/Rich CLI, MCP, static HTML reports generated from authorized views | All operator actions resolve to the same domain commands; report generation cannot change scientific state |
| Engineering checks | Ruff, type checking, pytest, Import Linter, generated-schema fixtures and targeted integration/fault tests | Enforce module boundaries, compatibility and the actual acceptance journey; measure behavior rather than test count |

Dependency versions are locked and qualified at implementation; source-review commits below are evidence references, not a claim that those versions have already been integrated. The server has its own supported Python version. Research projects keep independent Python and PyTorch versions within a published, tested compatibility matrix.

**Managed local infrastructure.** The installer provisions pinned binaries or uses explicitly selected existing services. The supervisor manages PostgreSQL, Temporal, the API and worker processes as one local installation. Use separate PostgreSQL databases/roles for the research ledger and Temporal persistence/visibility; a shared PostgreSQL process does not grant cross-database authority. Bind services to protected local interfaces and authenticate local callers. Start without an Elasticsearch dependency or a separate Temporal web UI. Capture service versions, configuration and health in `lab doctor` output.

One change from the earlier one-machine suggestion is deliberate: **the shipped product uses the regular Temporal Server, not `start-dev`.** Temporal documents `start-dev` as a development server that omits security checks; its default state is also ephemeral. A persistent `--db-filename` is useful for development and tests, but does not turn it into the production runtime. Temporal supports running its server binaries directly. Package a qualified single-node configuration with PostgreSQL persistence, supervised restart and backups. This is a local reliability commitment, not a high-availability claim. [Temporal CLI constraints](https://docs.temporal.io/cli/command-reference/server) · [Server deployment options](https://docs.temporal.io/self-hosted-guide/deployment) · [Server entry point](https://github.com/temporalio/temporal/blob/47409d6ee4a5f6b84e63d4e352bcb18e84c007c0/cmd/server/main.go)

**Local data and environments.** Keep configuration, credentials, service data, artifact blobs, job scratch and disposable caches in distinct directories under an operator-selected lab data root. The local artifact backend stages to private temporary files, verifies hashes and sizes, durably publishes bytes, then submits the manifest through the command service. Detect symlink escapes and prohibit arbitrary path reads through artifact APIs. No user project needs a server dependency or a mandatory OCI image. A uv environment isolates dependencies; the execution profile separately determines access to files, devices, processes and network. A failed dependency resolution explains the conflict instead of upgrading the researcher's packages silently. [uv workspaces](https://docs.astral.sh/uv/concepts/workspaces/) · [Python virtual environments](https://docs.python.org/3/library/venv.html)

**Supported local profiles.** Qualify macOS and Linux installations end to end. CPU execution is the portable reference. CUDA and MPS availability is discovered and tested for the selected project; exact numerical restore is never inferred from a device name. On macOS, host-native execution supports exploratory CPU/MPS work; the sealed profile uses a qualified local Linux VM and can evaluate on CPU when the model and plan allow it. Do not promise MPS passthrough into the VM. A model requiring a Linux GPU for evaluation needs a compatible Linux machine or optional remote runner, otherwise that plan remains unavailable. Windows/WSL support is a separately qualified profile, not an implicit v1 promise.

Model endpoints may be local or external. The chosen provider receives only authorized context and tool results under the project's data policy. A local install is not automatically an offline investigation when a hosted LLM is selected. Keep provider keys in the operator's secret store and issue scoped broker access to components. A component that creates synthetic data can have its own bounded LLM calls without owning the lab's credentials or unlimited budget.

## Codebase boundaries and reuse

[[codebase]]

Use one repository for coordinated lab packages and release tooling. Organize around responsibilities that change for different reasons: scientific rules, persistence, agent runtime, execution, transports and author-facing contracts. A uv workspace coordinates the lab's own packages; researcher environments are separate projects with their own locks. Avoid a generic plugin framework, global service locator or framework-wide base class as the component contract.

```text
apps/
  api/                         # sole research command/commit service + MCP adapter
  supervisor/                  # local installation, service and job lifetimes
  workflow-worker/             # Temporal coordinator and bounded turn workflows
  investigator-worker/         # model activities, context and proposed decisions
  assessor-worker/             # qualified plan conformance and assessment
  training-runner/              # executes in the research project's environment
  sealed-evaluation-runner/     # trusted launcher/scorer; restricted candidate child
  cli/                         # human and script client; no authoritative local bypass
packages/
  lab-domain/                  # pure rules and standard-library value types
  lab-application/             # command/query handlers and explicit ports
  lab-api-models/              # server-only Pydantic request/response models
  lab-persistence/             # SQLAlchemy, migrations, transactions and projections
  lab-orchestration/           # workflows, retry policy, versioned durable payloads
  lab-investigator/            # context builder, runtime port and provider adapter
  lab-runtime/                 # process, artifact, environment and sandbox adapters
  lab-reporting/               # authorized report views and HTML rendering
  lab-wire/                    # stdlib wire types; no Pydantic or server dependencies
  lab-worker-sdk/              # stdlib invocation, artifact and receipt helpers
  lab-pytorch/                 # optional integration with the project's existing torch
  lab-client/                  # CLI/external integration client
components/                    # reusable diagnostics, generators, rules, templates
schemas/                       # generated versioned JSON Schema + compatibility fixtures
tests/                         # contracts, recovery, security, workflow replay, journeys
evals/                         # private grader boundaries + public task runners
docs/                          # architecture, ADRs, author guide, operations, examples
packaging/                     # pinned services, OS profiles, install/upgrade/restore
```

These are ownership boundaries, not a mandate for one separately published distribution per folder. Publish worker-facing packages independently; consolidate server distributions when that reduces release work without violating imports or credentials. Each executable is a thin composition root. A feature follows a discoverable path from schema to command handler to domain rule to adapter and its relevant tests. Root contributor instructions explain those paths, runnable commands and the evidence required for changes; scoped instructions describe actual local constraints. Architecture decisions record a reason, alternatives and reversal conditions. Keep generated code labeled and reproducible.

**Enforced dependency rules.** Domain code imports neither frameworks nor infrastructure. Adapters depend on application ports; the application does not import a concrete adapter. Worker-facing packages cannot import server, database, Temporal or LLM libraries. CLI and MCP cannot import persistence or bypass commands. Import Linter checks those boundaries in CI. It does **not** enforce runtime authorization: PostgreSQL roles/grants, scoped API credentials and OS/sandbox policy do that. The command service gets `research_writer`; projection readers get restricted read access; migration ownership is a distinct maintenance role. Investigator, assessor, workflow and training processes normally have no research-database credentials. [Import Linter](https://import-linter.readthedocs.io/en/stable/) · [PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html)

**The worker compatibility promise.** `lab-wire` and `lab-worker-sdk` use the standard library. `lab-pytorch` uses only those packages and the project's already-installed PyTorch; it must not pull a different torch/CUDA build or require Pydantic v2. Server boundary models generate versioned JSON Schema. Worker fixtures are checked against those schemas in a separate test environment, and the server validates received messages. A schema major and supported Python range are explicit. Projects outside the importable SDK range can use the documented JSON subprocess protocol and a small project-owned adapter. Dependency-free is not a promise that every historical Python or PyTorch version works.

### Reuse decisions grounded in source

Prefer an upstream dependency for a stable primitive, an adapter for an existing research framework, and a documented pattern when importing an entire runtime would impose the wrong ownership model. Pin source revisions when studying behavior. If we copy or fork code, preserve the applicable license and notices, record origin and modifications, add the relevant conformance fixtures and assign responsibility for upstream fixes. The release includes dependency/license inventory. Do not import a repository's internal modules simply because they happen to be reusable today.

## The research loop

[[research]]

**The study charter precedes exploration.** Commit an immutable charter revision before task-specific exploratory trials are admitted. It fixes the target population and comparison, metric identity/direction/denominator, minimum useful effect, permitted regressions, resource limits, and the decision standard, including uncertainty, multiplicity and stopping policy where applicable. Record the observations already known at charter creation, including imported model results. Choosing a candidate during exploration is allowed; choosing its pass/fail bar after seeing its effect is not a prospective success rule.

**Evidence plans inherit the charter.** Every plan pins the charter revision, digest and success-rule reference. The resolver materializes those rules, and admission rejects a plan or template that overrides them. Sample sizes, seeds and logistics can be resolved before freezing under the charter's predeclared design policy; any choice informed by observed results is retained as exposure metadata. Missing success criteria permit exploratory work only after an exploration-only charter is recorded, and cannot later be portrayed as pre-exploration criteria for that work.

**Later changes are exposure-informed.** Amending a threshold, guardrail, metric, target, comparator or decision standard creates a new charter revision with the previous values, rationale, author and exposure-event references. Preserve the original rule and assessments. Mark the amendment exposure-informed when relevant results have been seen, including by a human. A new study ID does not erase those exposures. A new plan can test the revised rule on fresh independent data, while continuing to report that the rule was selected after exposure. A newly discovered question outside the charter follows this same route.

**The unit of scientific comparison is a trial under a protocol.** The study links its charter to dataset/split identities, comparison unit, search budget and baselines. A change to the evaluation contract creates a new comparison group and can rescore retained predictions when eligible. Rescoring old evidence under a new bar remains an exposure-informed analysis.

1. **Import, charter and reproduce.** Register the project's model factory, evaluation command and already-known results. Commit the charter before new task-specific exploration. The adapter describes how to load an example, collate a batch, interpret an output, obtain targets, build the model, and save or load its state. Capture a reference batch, include modes such as evaluation versus training, and check output equality to a declared tolerance in a fresh worker. A bare state dictionary triggers a request for builder and preprocessing information. A project offering inference only can still run probes and paired tests.
2. **Locate the failure.** Ask for example IDs and per-example scores before choosing a remedy. Candidate explanations include faulty labels, a shortcut, a representation that loses information, an ineffective update, and an evaluator mistake. When appropriate, measure intermediate activations, gradients or update norms at named points on a small fixed batch. Compare the instrumented and uninstrumented behavior and cost. Compute on the worker, return a statistic, a few cases and an artifact handle. Keep activation capture bounded by layers, examples, precision and byte limits.
3. **Generate different ways to learn.** A proposal may return a new model builder, an attributed source patch, weights derived from a parent, a new data generator, an optimizer with additional persistent state, or an entire training step. A researcher can supply conditional search spaces and symbolic transforms. For arbitrary Python, the escape hatch is a new source revision and fixture. The investigator can author a new component inside a restricted build job, run its conformance tests, then bind it on a candidate branch.
4. **Qualify before paying for scale.** Check shapes, finite outputs and gradients, task-specific invariants, serialization, and the declared parameter, memory or latency envelope. For a causal sequence model include a future-token perturbation test. A failed qualification retains its failure and generated source. Preserve code, seed and parentage for candidates discarded early.
5. **Allocate comparable trials.** Run the current best model and a simple or random-search baseline. Pair seeds and data order where meaningful. Select the compute measure appropriate to the question: equal training examples isolates sample efficiency, equal accelerator time tests practical efficiency, and both matter when a new update doubles the work per step. Record actual tokens/examples, optimizer steps, device time, peak memory and quality at matched points. A replaceable policy can prune or promote using development results. Periodically run some early losers to full budget to estimate whether the cheap screen discards late learners.
6. **Confirm and export.** Freeze candidate and analysis before final evaluation. A separate evaluator measures prespecified accuracy, failure slices and resource tradeoffs on fresh seeds and held-out cases. Pair comparisons by task unit, report uncertainty and variation across seeds, and state the scope of any improvement. A frontier of quality, latency and memory can be more useful than a single winner. Export builder, preprocessing, weights, inference checks, environment lock and a recipe for the evaluation. Record negative results and the count of candidates tried.

**Scientific decision rule.** Apply the success criteria inherited from the pre-exploration charter. For device data, split by device or collection site when that matches the deployment question; thousands of events from one device do not provide thousands of independent device-level observations. Keep common validation data available for search and limit how often confirmation outcomes are revealed. If the measured range includes both material benefit and harm, record an inconclusive result and identify the cheapest discriminating next trial. A lead selected using development comparisons earns its final claim on independent confirmation under the recorded charter revision.

**Freedom during exploration.** Record the purpose of a run before dispatch, including reproduction, measurement development or open search. Hypothesis-driven experiments should record competing predictions and what would change the next decision. A fixed number of rival hypotheses is not an admission requirement. Exploratory observations can guide the next run immediately. Stronger assertions use the evidence-plan process below.

**Fair tuning and disclosure.** Declare tuning opportunities and budgets for each arm, including prior search that selected the candidate. Choose appropriate hyperparameter spaces for each method and explain differences; identical ranges can disadvantage a different optimizer. Report training efficiency and total research cost separately. Track which development, generator-feedback and monitoring results were disclosed to each operator and when. A human who sees a monitoring score can influence later choices, so that disclosure belongs in the same record as an LLM-visible score. Count adaptive comparisons, but label any numerical estimate of selection inflation with its assumptions. Keep confirmation access bounded under a frozen plan. Fresh samples from one synthetic generator do not test that generator's assumptions. [Adaptive holdout reuse](https://arxiv.org/html/1506.02629) · [Leaderboard feedback and adaptive selection](https://arxiv.org/html/1502.04585)

**Why allow both source edits and structured search?** EvoPrompting used language models to mutate architecture code. PyGlove implements reusable rules on compatible symbolic objects; NASLib offers explicit sampling, mutation and query hooks on its graph abstraction. Those are good optional methods for a project able to use them. Li and Talwalkar found competitive random-search baselines in their studied spaces. I would make a baseline and an independently reproducible comparison conditions of a discovery claim. A source difference alone establishes a new candidate revision. A broader novelty claim also needs comparison to related methods. [EvoPrompting paper](https://papers.neurips.cc/paper_files/paper/2023/file/184c1e18d00d7752805324da48ad25be-Paper-Conference.pdf) · [PyGlove implementation](https://github.com/google/pyglove/blob/58059695c81b80109bb08b85e14192680d016456/pyglove/core/patching/rule_based.py#L98-L129) · [NASLib graph](https://github.com/automl/NASLib/blob/8cb5d2ba1e29784de43039d9824c68e88fb1a1da/naslib/search_spaces/core/graph.py#L844-L860) · [Random Search and Reproducibility](https://proceedings.mlr.press/v115/li20c.html)

**A decision the earlier switch experiment actually supports.** An ordinary classifier averaged event vectors and scored 98% on the original synthetic traces, yet solved zero opposite-order pairs. Algebra explains why a permutation disappears in the average. A position-weighted average with the same 86 parameters learned a usable order signal. Setting its final recorder coefficient to zero after training solved all 4,000 fresh pairs at each of three seeds. The profitable next operation was a weight edit on a copy. This CPU investigation was directed in chat. It supplies a concrete acceptance fixture for the design; autonomous discovery and general superiority still need measurement. [Original runnable experiment and saved results](pytorch-lab-worked-example.zip)

**How a new study would run.** A researcher brings an event classifier from a second device. The investigator first tests whether the input representation retains fine timing. If a time-preserving probe succeeds while the trained readout fails, try readout/weight intervention and a changed learning signal. If a pair is indistinguishable before readout, propose two structures: a small learned temporal filter and a recurrent update with persistent per-sequence state. Validate masks and state reset at sequence boundaries. Train both against the baseline on matching budgets, include a shuffled-time control, and measure on held-out devices. A positive result advances one candidate to confirmation. Evidence that device-specific features explain the gain sends the investigation back to data or evaluation.

## Claims and evidence plans

[[claims]]

**A finding has a scope and an evidence requirement.** “This edit improved this checkpoint,” “this input contributed to its errors,” and “this training recipe usually learns an unused capability” are different assertions. Record them as separate claim revisions. A successful local repair does not silently become a general explanation or an architecture-discovery result.

The evidence planner expands a versioned protocol template into an inspectable plan. The resolver locks executable dependencies; the command service admits its work. An independently authorized protocol assessor checks realized runs against that frozen plan. The researcher owns the scientific assumptions and policy for promoting a finding. An LLM may propose an explanation or draft a protocol, but it cannot grant its own code authority to assess a claim.

| Object | Required contents |
|---|---|
| Study charter revision | Pre-exploration success rules, population/comparator, metric meaning, guardrails, decision standard and budget; known exposures at creation; later amendments with exposure-informed provenance. |
| Claim revision | Statement, kind, model/task/population scope, fork point if relevant, author, assumptions, alternatives, supporting and contradicting evidence, and superseded revision. |
| Protocol template release | Input claim schema, applicability checks, plan-expansion code, required controls, analysis/assessment capability and executed qualification receipts. Promotion requires planted-effect detection and null-case silence before authorization for specified uses. |
| Evidence plan | Claim and charter revisions/digests, inherited success-rule reference, template digest, arms/interventions, checkpoint parents, tuning spaces/budgets, seed policy, analysis unit, splits/exposure, resource reservation and unresolved logistical obligations. |
| Qualification record | Exact template/assessor/environment and control-suite digests; independently maintained planted-effect and null fixtures; expected behavior, realized outputs, repetitions and acceptance criteria fixed before qualification. |
| Execution receipts | Exact run locks and artifacts; actual examples, updates, data composition, hardware, costs and deviations. A successful job can still be ineligible for a comparison. |
| Assessment | Frozen plan digest, assessed evidence set, conformance findings, effect estimates/uncertainty, outcome, assessor identity/release, remaining alternatives and scope. |
| Support justification | The specific observations, assumptions and assessments jointly required for a conclusion. Multiple independently sufficient justifications may support one claim. Shared dependencies remain visible. |

**Two independent state axes.** Assessment outcome is unassessed, protocol-passed, protocol-failed or inconclusive. Evidence health is intact, affected or withdrawn. A third field records execution conformance as conformant, deviated or incomplete. A deviation can force an inconclusive outcome under the plan's rules. A protocol-passed claim whose scoring method is later withdrawn retains its historical assessment alongside unhealthy evidence; the current view must show both. Protocol failure does not establish the opposite claim. A missing artifact can prevent replay without refuting retained measurements.

### From a proposed finding to an assessed result

1. **Draft.** An operator files a scoped claim and selects a qualified template. The planner takes its success rules from the pinned charter and produces arms and an estimated cost. A draft can have unresolved logistics, but its success bar cannot be chosen from its exploratory results.
2. **Qualify.** Check charter compatibility, template applicability, passing planted/null qualification receipts, comparison units, data access, tuning opportunities and component qualification. A proposed causal explanation lists plausible alternatives that its controls would leave unresolved.
3. **Freeze and admit.** The command service verifies the inherited charter rules, immutable qualification receipts, current policy and resource reservation, then commits the frozen plan through the single write path. A qualified and approved template can run automatically within project policy. Human authorization alone cannot qualify novel assessment code.
4. **Execute.** Temporal coordinates ordinary trials, private checkpoint branches and sealed evaluation. The investigator can inspect permitted progress, while protected outcomes follow the plan's disclosure rules. Pause, cancellation and partial evidence retain explicit status.
5. **Assess.** The assessor reads receipts and allowed evidence, verifies charter/plan conformance, runs the qualified analysis and submits an assessment to the command service. The service fences and commits the result. A changed success rule requires an attributed charter amendment; a changed execution/analysis plan preserves the charter relationship and exposure history.
6. **Reuse or revise.** Publish the bounded statement, assessment, evidence health and limitations together. A later project can use it as a prior or propose a transfer study. Catalog retrieval also includes exploratory ideas, counterexamples and failed attempts with their status visible.

**The assessor checks a protocol; scientific interpretation remains scoped.** Built-in templates include improvement under a resource bound, intervention effects on a failure, feature decodability, and transfer to another population. A feature being decodable does not establish that the model uses it. A targeted intervention plus a restoration and specificity control strengthens a mechanistic account but cannot exclude every alternative. Function-preserving tests apply to transformations that promise preservation. A mathematical impossibility argument is reviewed with its assumptions and model semantics; finite empirical failures alone cannot prove impossibility.

For an improvement claim, use the baseline/comparison, minimum useful gain, tolerated regressions and decision standard in the charter. Estimate sample needs at the relevant unit under its design policy and account for uncertainty in a small pilot; observed pilot effects cannot silently lower the required gain. For a mechanism claim, choose controls that test actual competing explanations. A same-size weight edit is one possible control, not a universally equivalent intervention. For a transfer claim, a new sample from the original generator may be insufficient; the new task, generator or population must match the proposed scope.

### An executable plan is also a component output

A planning component implements `evidence-plan/1`: it consumes a typed claim, pinned charter and bounded study view, then returns a draft with inherited success rules, artifact references and unresolved logistical obligations. The command service stores the draft and controls admission. An assessment component implements `protocol-assessment/1` and requires the project's assessment grant. The planner's and assessor's releases are pinned separately. A researcher can add a new template for an unusual learning rule without changing the ledger or writing a new orchestration system, subject to the qualification gate below.

### Qualification before template or assessor approval

**Executed positive and null controls are mandatory.** Before any template or assessor release can be approved for scientific assessment, an independent qualification runner must show that the applicable pipeline detects a known planted effect and stays silent on a known null case. For a template, exercise plan expansion through execution and assessment, so a correct-looking plan cannot pass while producing invalid conclusions. For an assessor, provide controlled evidence/receipt inputs and verify the expected decisions. Test the intended template/assessor pairing as well as each release's contract.

The control suite fixes planted effects, null conditions, expected outputs, repetition counts and acceptance criteria before the qualification run. A deterministic positive must detect its planted effect and a deterministic null must not assert one. For stochastic procedures, require the prespecified detection power and false-positive bounds across repeated controls, reporting uncertainty; one lucky positive and one quiet null are insufficient. Include relevant grouping, noise, missing-data and invalid-receipt cases for the approved scope. A mismatched or incomplete qualification produces a failed or inconclusive gate, never approval.

Store immutable qualification receipts linked to exact code, dependencies, control-suite and environment identities. The command service's promotion handler checks these receipts before accepting an authorized approval. A human signature cannot bypass the gate. New or changed templates/assessors must qualify for their requested scope; an unqualified method may remain project-local and exploratory but cannot issue authoritative protocol-passed assessments. If controls cannot yet be constructed, qualification is unfinished and promotion remains unavailable. Existing approvals are suspended for affected uses when supporting controls or releases are withdrawn.

**Independent authority and honest evaluation.** The assessor uses project-approved code in a distinct execution identity. Candidate inference remains isolated from labels and trusted scoring. Assessment plugins run in restricted workers with the minimum grants, never as arbitrary code loaded into the command service. If an open-ended task requires a model or human judge, version the rubric, measure judge reliability on relevant controls and include that uncertainty. Model-generated observations can support an appropriately validated measurement; fluent self-approval cannot substitute for qualification.

**Exposure and support are durable records.** Development feedback may guide search. Generator-feedback data may guide data creation; record any overlap with selection data and choose separate sets when the question requires independence. Monitoring results disclosed to humans count as feedback if they can influence the investigation. Confirmation results released repeatedly need an explicit reuse policy. Do not infer a universal overfitting penalty from a comparison count alone. [Adaptive data analysis](https://arxiv.org/html/1506.02629)

When a defect is reported, traverse typed support dependencies and apply the affected-condition predicate. Mark affected assessments for reassessment and queue eligible rescoring with estimated cost. Replaying identical outputs can establish equality for those retained inputs only; it cannot prove global semantic equivalence or repair a flawed assumption. An unaffected sufficient justification can keep a claim supported. Unsupported means its current support is inadequate, and does not mean the statement is false.

## The component contract

[[component]]

**A component is a versioned executable research capability that declares what it needs, what it can change, what it produces, and how its behavior can be checked.** A release bundle can carry several exported components. A capability is the semantic contract, including input and output meaning; a component release implements it. A run is one invocation of a resolved release. An artifact is data produced or consumed by a run. A claim is a scoped statement, an evidence plan specifies how it will be assessed, and an assessment records what that plan established. These identities have different lifetimes.

| Execution form | Example / public promise | Placement and result |
|---|---|---|
| Artifact operation | Score prediction pairs, edit a checkpoint, generate a dataset, propose a new builder | Isolated job consumes immutable inputs and publishes a typed output manifest. Composes naturally across repos and languages. |
| Training extension | Change an update, capture an activation, perform model surgery before optimizer creation | Versioned callable loaded inside the trusted boundary of that trial's worker. Adapter declares phase, state read/write sets and resume contract. Tensor work stays in-process. |
| Decision policy | Choose the next observation, candidate or amount of training | Given a bounded study view, returns a proposed action, rationale and stop condition. The command service independently checks authorization, expected revision and remaining budget. |
| Managed service provider | Model inference, checkpoint I/O, trusted compute submission | Operator-installed provider implements a narrow port. A run obtains a scoped, metered handle. A project author can select approved implementations and cannot install privileged infrastructure through a research-worker wheel. |

**Execution form and scientific effect are separate axes.** The form determines where code runs and how it is supervised. Effects describe what it changes in an investigation. Declare all applicable effects and concrete read/write sets. “Observe” means the source experiment is protected; a probe can still train an auxiliary model, use gradients or intervene on its private copy.

| Scientific effect | Example | Required boundary or evidence |
|---|---|---|
| Observe | Pair scorer, gradient probe, activation intervention | Declare model mode, gradient requirements and private mutations. Preserve the source model, buffers, optimizer, data cursor and RNG streams. |
| Generate or change data | Synthetic cases, filtering, curriculum | Publish immutable data lineage, validation results and realized group counts. Record both requested and achieved distributions. |
| Change weights | Readout edit, head retraining | Child checkpoint names its parent, edit and preserved/dropped state. A weight edit can need no further training. |
| Change learning | Optimizer, loss, stateful update | Declare phases, state ownership and composition. Additional computation and resume behavior enter the comparison. |
| Change structure | New builder, graft, module replacement | Declare preservation or intentional discontinuity. Require function preservation only when promised; validate task-specific invariants and export behavior. |
| Plan or assess | Search policy, evidence-plan template, statistical assessment | Proposals use normal admission and inherit charter rules. Template/assessor authority requires executed planted/null qualification and a separate promotion grant. |

An activation probe is typically an artifact operation with an observation effect. A graft can be a construction-time training extension with a structure effect. An LLM-backed generator remains an artifact operation with a data-generation effect. An evidence template is a planning component. Implementation language, use of an LLM, execution form and scientific effect are independent attributes.

A pure Python method, a method that calls a model once and a bounded specialist loop all fit the same contract. For a specialist declare the callable model role, exact resolved model identifier where available, prompt revision, access, limits, state and stopping rule. Attribute child usage to its parent. Persist generated candidate bytes and model responses according to retention policy. A hosted model alias can drift; label replay from stored outputs separately from regeneration.

### What an author ships

A Python wheel, source bundle or subprocess adapter carries a manifest, entry point, machine-readable input/output schemas, scientific semantics, and fixtures with expected outcomes. Local v1 records source and independently resolved environment locks by digest; OCI images are an optional execution form. Include a wire/SDK compatibility range, licensing metadata, resource requirements, requested grants, supported isolation requirements and state-schema versions. Build receipts link reviewed source, environment and executed qualification. A package digest establishes identity; scientific qualification requires controls appropriate to the intended use. A worker-facing release cannot acquire server dependencies or privileged grants merely by declaring them.

| Contract field | What an author supplies |
|---|---|
| Question and limits | A method card explaining which question it addresses, required assumptions, known failure modes and conclusions it cannot support. |
| Ports and semantics | Required/optional capabilities, schemas with units and metric meaning, model sites/phases and compatibility requirements. |
| Effects and isolation | Read/write resources, private mutations, external effects, model mode, RNG policy and conflicts with other components. Declarations inform planning; process and service boundaries enforce access. |
| State and lifecycle | Owned state schemas, serialization, parameter mappings, cancellation boundary and supported restore/migration classes. |
| Cost and observations | Estimated resource envelope plus actual time, examples, updates, tokens, memory and relevant realized conditions. Estimates are compared with receipts. |
| Qualification | Positive and negative controls where meaningful, failure fixtures, ownership of each test and independent challenge evidence for supported uses. |

```python
def run(inputs, config, *, reader, writer):
    counts = {}
    for row in reader.rows(inputs["predictions"]):
        group = counts.setdefault(row[config["group_by"]], [0, 0])
        group[0] += 1
        group[1] += int(row["pred_a"] == row["label_a"]
                        and row["pred_b"] == row["label_b"])
    return writer.stage_json("report", counts)
```

This abbreviated contract uses decoded binary decisions. The upstream decoder records the threshold, tie behavior and label mapping. The full schema requires unique pair IDs, two valid labels and a non-null grouping column; it declares the report’s pair order as total followed by both-correct. Validation rejects malformed input. The runner checks the staged output schema before publication. A replacement that streams the rows and yields the same counts can implement the same contract. Changing the numerator to “either correct” creates a different metric identity even if the output JSON shape matches.

**Qualification is staged.** A project-local component can run in a sandbox after interface and resource checks, with its qualification status visible. Promotion to a supported scientific method requires relevant independent controls, including planted or null cases where they exist. Tests written by the same investigator remain useful author tests and are identified as such. For a default investigator catalog, measure whether the component helps an operator reach better decisions on held-out tasks; correctness alone does not establish usefulness. These requirements scale with the claim and method. A storage provider needs integrity/failure tests, while a novel exploratory probe may initially have no established scientific null.

The flexibility above applies to exploratory methods. Every template and assessor seeking authoritative assessment approval must pass both the planted-effect and null gates specified in the claims section; no general component-qualification exception relaxes that requirement.

Independent qualification records the origin and access history of its controls. Calling another instance of the same LLM does not by itself make a test independent of the method's assumptions or development data.

### Inside a researcher’s model adapter

Start with the author’s existing `build(config)` and `predict(model, batch)`. An adapter names immutable fixtures and the model-input and output contracts. A training-capable adapter additionally exposes `train(plan, context)` or a smaller step interface and its supported phases. Where existing code owns an unusual optimizer, custom autograd function or multi-optimizer schedule, the full trainer can run as a process and publish standard observations and checkpoints at boundaries it actually supports. The researcher controls the mathematical definition of a step. The SDK never assumes that all models return logits, that batches are tensors, or that one batch means one optimizer update.

Consider an author writing a new update rule that retains a moving estimate of gradients from rare failures. It requires two identified training groups, owns a buffer with schema `rare-gradient/1`, and declares when it reads the globally reduced, unscaled gradients. The adapter must say whether a group-specific gradient exists at that point. When it does not, the author can implement a complete training step that exposes one; returning the combined gradient under the old name would change the method. Compare three trials: the original optimizer, the same extra group-gradient computation with the memory term disabled, and the full update. Match training examples and report added runtime. An inference export depends on the final architecture and tensors. Resuming this training procedure also depends on the memory buffer and its update implementation.

### Author, install, replace, remove

1. A human or external agent authors components in a project workspace, runs the local contract suite, then submits an immutable source bundle through the same publishing route. A remote MCP host exchanges an upload grant or a registry digest; a laptop path alone has no meaning on the worker.
2. A builder resolves dependencies in a separate project environment, runs tests, records source/environment digests and its achieved isolation, and publishes through the command service. Dependency isolation alone is not a sandbox. Validation includes negative fixtures, deterministic checks where promised, bounds, and a restore fixture for stateful methods. Installation exposes metadata for discovery. Enabling it changes a specific project profile revision. Package installation and build scripts are code execution and receive the selected execution profile's restrictions.
3. Before a run, resolve all required providers and artifacts, verify grants, materialize an execution lock, and reserve budget. On a long investigation, the next decision can discover a newly enabled scorer and apply it to old predictions. An in-flight trial continues under its pinned lock.
4. Replacing a default affects subsequent resolutions. To change a running trial at step 8,000, save a checkpoint and fork from it. The migration declares which states are copied, transformed, initialized or dropped. Run fixture comparisons and record lineage before promoting a child. If compatible resume fails, offer an explicit warm start or fresh training.
5. Retirement hides a release from new profile bindings. Retain blobs needed by live jobs, exported models and retained evidence. Replacing or retiring a sound release does not invalidate its historical results. A scientific withdrawal names the defect, affected releases, conditions and evidence dependencies. A metric bug can require rescoring; a training-rule defect may require new training. Append corrections and reassess affected support without overwriting history. A claim with another sufficient, unaffected justification can retain support.
6. Purging restricted or revoked code is an explicit operation with affected dependents, execution restrictions and tombstones. Mark a historical model unrestorable if indispensable code was purged; that alone does not make its retained observations false. A security revocation can stop jobs immediately under policy. A scientific defect pauses or quarantines only affected work at an appropriate boundary. Material changes to running scientific behavior create a branch.

## Dependency injection and extension boundaries

**Yes to dependency injection; use an explicit per-run resolver in the Python lab.** The control plane has a composition root where the operator chooses implementations for storage, model routing and job dispatch. The research SDK takes named constructor or keyword arguments for its declared ports. Worker-local implementations resolve to Python objects; cross-process services resolve to short-lived authenticated clients. Inject a reader for the declared input artifacts, or a model client billed to this run. A scientific dependency such as a particular dataset is an immutable input reference. It belongs in the evidence graph even when a reader is injected to open it.

DeepSeek's vendored Cordis records required implementations per plugin instance and owns lifecycle cleanup. Its documentation explicitly specifies teardown when a required service disappears and reload when it returns, and demonstrates isolated service groups. I would reuse those exact concepts for a DSH-based investigator host, if selected. For scientific jobs I would bind release identity once and make failure/recovery visible. A network reconnect to the same authorized service identity is fine; substituting a different scientific provider opens a new attempt or trial under explicit equivalence or migration rules. **Resolution rules.** Resolve by capability major version, implementation digest, project binding, hardware, grants and state compatibility. Precedence is an authorized explicit trial override, then the pinned project profile, then an operator default frozen in that profile. Required ports have exactly one binding unless the contract declares a collection. Ambiguity, dependency cycles, missing grants and unsatisfied hooks are planning errors. Missing optional ports resolve to an explicit absent value with a documented fallback recorded in the lock. Validate transitive dependencies. Build independent worker environments for incompatible Python/CUDA requirements. Two versions that must execute inside a single interpreter must have a satisfiable environment or become separate trials.

**Example resolved invocation.** A release named `paired-report/1` might be implemented by local Python on a laptop and a batch reader in a hosted lab. A resolver emits the selected method digest, entry point, schema digests, exact reader/writer implementations, referenced dataset digest, full config, access class, execution environment, budget reservation, and optional-port decisions. IDs such as `profile:17`, `component:by-group@sha256:…` and `reader:parquet@sha256:…` are kept individually so one can tell which binding changed. Secret values are issued at runtime; the lock records grant scopes and service identity. A fixture can replace the reader with an in-memory fake without mocking the whole harness. Before dispatch, a missing `paired-labels/1` contract produces a diagnostic naming the consuming component, available column semantics and any approved adapter.

**Hook ordering.** A trainer adapter exposes named phases such as before optimizer construction, after gradient unscale and distributed reduction, before optimizer step, and after successful step. It states the precise meaning under gradient accumulation, mixed precision and sharding. Components declare reads, writes, required ordering and optional compatibility with compilation. Two gradient writers with no defined composition fail resolution. Hooks that propose new parameters must also declare optimizer-state mapping and distributed-wrapper implications. Validate phase counts on a short synthetic batch, then construct and pin a total order. The inner loop performs direct calls; MCP, Temporal and database writes stay outside the tensor hot path. Composer's event interface and required-on-load mechanism show why those two concerns belong together. [Composer algorithm API](https://github.com/mosaicml/composer/blob/6405188805a0054b4551ec49e4919c54c971d0e8/composer/core/algorithm.py#L20-L65) · [Required algorithm restoration](https://github.com/mosaicml/composer/blob/6405188805a0054b4551ec49e4919c54c971d0e8/composer/core/state.py#L1124-L1155)

**Scopes.** Deployment owns trusted service adapters. Project owns profile and policy. Investigation owns question, budget and notes. Trial owns immutable plan and scientific inputs. Attempt owns lease, credentials, scratch directory and particular execution. Rank owns device and per-rank training state. Cleanup of a scope releases its handles and scratch resources. Durable jobs and artifacts have explicit owners and retention rules, so a client or investigator stopping cannot accidentally dispose of a GPU job.

**MCP is an operator interface.** The canonical API is a set of domain commands and queries. The UI, CLI, internal investigator and MCP adapter all reach the same authorization, validation, budget and idempotency logic. The gateway exports a small stable set of tools. Installed scientific methods are discoverable as versioned data with schemas and examples. Installing 500 generators therefore does not put 500 tool definitions into the investigator’s context.

**Retry and concurrency.** JSON-RPC `id` correlates a single exchange. The domain `command_key` survives reconnects. Store a unique (tenant, project, authenticated caller, command key) entry and a normalized payload hash in the same transaction as the command. A replay of the same payload returns the same receipt; a changed payload with that key returns a conflict. Cross-operator handoff uses the existing investigation ID. ## Bounded investigator turns and recovery

[[turns]]

**Long investigation; short agent runs.** A durable investigation coordinator schedules a bounded child workflow for each decision turn. The child runs model and tool work as activities and ends after its action/call/time/token limits or a durable wait condition. It does not remain alive through a three-day training job. Admitted jobs have independent durable identities and lifetimes; their completion wakes the coordinator for another turn. A specialist component may use the same bounded pattern, charged to its parent budget. No essential investigation state exists only in an agent object, Python kernel or conversational summary.

Before starting a turn, the command service commits a `TurnSpec`. The context builder reads the authorized ledger and artifact views at that specification's horizon. The investigator may make several model calls within the bounded turn, recording each accepted decision and its tool-call ordering before executing effects. Completion stores the turn result through the same command API. The next turn reconstructs context from evidence, pending jobs and steering, including newly enabled components. An existing trial retains its old lock. Installing a method is not permission to replace scientific code mid-run.

| Turn record | Required contents |
|---|---|
| Identity and source horizon | Project, investigation, turn ID, expected study revision, ledger horizon and authorized source-manifest digest; append permitted observations received during the turn |
| Context | Context-builder version/configuration, exact packed context artifact, retrieval selections and omissions, summary provenance, ordering and truncation decisions |
| Runtime and methods | Investigator policy/runtime release, model/provider settings, stable tool adapter schemas, component catalog snapshot and project bindings |
| Resources | Deadline, model/tool/token limits, remaining global budget, reservations and exposure/access policy |
| Decisions | Persisted decision IDs, accepted outputs, ordered tool calls, command keys, payload fingerprints, receipts, unfinished handles and stop reason |

**Stable tools, changing component catalog.** Register a small tool vocabulary when constructing the runtime: inspect evidence, search/describe components, submit a typed invocation, query a job, and propose a plan or branch. Catalog entries are data selected under the turn snapshot. Thousands of installed methods do not become thousands of workflow activity types or prompt tool definitions. Pydantic AI's current docs allow pre-registered dynamic toolsets under determinism restrictions; that does not remove deployment-name and payload compatibility requirements. Preserve deployed agent/toolset names and retain schemas/worker versions needed by in-flight work. [Pydantic AI Temporal constraints](https://pydantic.dev/docs/ai/capabilities/durable_execution/temporal/)

**History and payload control.** A bounded child prevents unbounded per-agent history, but the parent still accumulates events. Continue-As-New the parent before its history thresholds, after draining handlers, carrying only compact durable references and a consumed-event cursor. Process missed events from the command service's durable inbox after rollover; do not rely on an unacknowledged signal as the only copy. Job workflows survive turn closure and coordinator rollover under an explicit lifecycle policy. Global budgets, exposure and command identity remain in the ledger and never reset with workflow history. Temporal documents limits of 51,200 events or 50 MB per workflow history; operate well below both and test the configured thresholds. [Continue-As-New](https://docs.temporal.io/develop/python/workflows/continue-as-new) · [Workflow limits](https://docs.temporal.io/workflow-execution/limits)

Pass artifact handles through workflow payloads and model context, with bounded previews obtained by authorized tools. The LLM must still be able to inspect meaningful examples, code and plots. “Handles” is a storage/transport rule, not a prohibition on seeing evidence. Preflight serialized arguments, results and errors against an application envelope below the service limits; store oversized content as artifacts before the workflow boundary. The Pydantic AI documentation warns that oversized inbound payload failures can repeatedly fail workflow tasks. A finite activity retry policy alone does not fix that path. Validate the boundary and exercise deliberate overflow tests. [Payload and serialization constraints](https://pydantic.dev/docs/ai/capabilities/durable_execution/temporal/)

**One transport retry owner.** Set provider SDK `max_retries=0` and disable nested transport retries in the Temporal-backed runtime. Temporal activities get explicit finite attempts, deadlines, backoff and non-retryable error classes. Temporal's `maximum_attempts=0` means unlimited, not disabled. Model-output repair is a separate bounded semantic action with recorded calls and costs. A provider timeout may leave unknown spend; retain that uncertainty and reconcile by provider request ID when supported. Do not equate a retry with a free or identical generation.

**Cancellation and upgrades.** Stopping a turn cancels its child workflow and propagates cooperative cancellation to activities; it cannot undo committed effects or guarantee a provider has stopped charging. Pausing an investigation prevents new turns and applies the recorded running-job policy. Canceling training requests backend termination and reconciles actual completion. A newly qualified runtime/context policy applies at a new turn boundary. In-flight turns stay on their pinned runtime or undergo an explicit compatible migration. Parent workflow code separately needs Temporal-compatible versioning and historical replay tests; short turns do not solve parent upgrades automatically. Stored tool validation and message schemas must remain readable until affected work is drained or migrated.

**Runtime qualification is a release condition.** Exercise every supported model provider, including the actual OpenAI-compatible endpoints; interruption before and after a committed tool effect; turn/workflow/job cancellation; a catalog larger than the model's practical tool budget; component installation between turns; provider/runtime and parent-workflow upgrades during an investigation; payload rejection and history rollover; and recovery with exhausted budgets. Pydantic AI is the selected first adapter, not the authority boundary. If it cannot satisfy these cases, replace that adapter with direct provider SDK activities behind the same port. Keep DBOS as an architectural fallback, not a parallel implementation project.

### Stable intent before effects

Use a stable command identity derived from the recorded logical call, for example:

```python
import hashlib
import json

def command_key(project_id, turn_id, decision_id, call_index, subcommand_index=0):
    identity = ["lab-command/1", project_id, turn_id, decision_id,
                call_index, subcommand_index]
    return hashlib.sha256(json.dumps(identity, separators=(",", ":")).encode()).hexdigest()
```

The indices come from the **persisted accepted decision**, never an in-memory counter or parallel completion order. A retry loads that decision and resubmits the same key and arguments. If a lost model response must be regenerated before any decision was accepted, it gets a new decision identity; the old unaccepted response had no authority to execute tools. Enforce a unique acceptance slot and fencing epoch so a late concurrent response cannot execute a second decision for that slot. Persisting the whole accepted call batch before dispatch also prevents a crash halfway through parallel calls from changing their identities.

Store the normalized payload fingerprint beside the key. Same key and payload returns the original receipt or pending status. Same key with changed payload is a conflict. Different keys with identical payloads can be intentional repeated trials, so the payload hash alone is not the operation identity. External CLI/MCP callers persist their own operation IDs and need no synthetic turn ID. Service retries use a stable logical principal, not the current process credential instance. Receipt access is still authorized for the requesting caller.

The command transaction atomically records intent, scientific changes, reservation and outbox event. Backend dispatch uses the admitted job/attempt identity and queries its status after an ambiguous timeout. A command receipt prevents duplicate admission; it does not promise exactly-once execution across an arbitrary external system. When a backend cannot deduplicate or reconcile, report `OUTCOME_UNKNOWN` and account for possible spend before a replacement launch. Retain command identities for as long as scientific history may be replayed, independently of Temporal retention. [Idempotent API design](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### Recorded turns as an evaluation dataset

Version the context builder as executable policy. Retain both the actual packed context and an authorized source manifest as of the original horizon. The packed prompt alone cannot test whether a different retriever would have found omitted evidence. Replay an evaluation turn with a different context policy or investigator model using only information available at that point, under equivalent budgets and permissions. Use fresh evaluation IDs and an isolated namespace; never let a benchmark replay resubmit production commands.

Distinguish three tests. **Recovery replay** asks whether orchestration resumes the recorded execution correctly. **Offline decision evaluation** asks whether a policy makes better grounded choices from the permitted past. **End-to-end research evaluation** executes those choices in a task environment and measures their consequences. A new policy that chooses an unrecorded experiment does not inherit the result of a different historical experiment; run it, use an explicitly validated simulator, or mark its outcome unknown. Multiple scientific paths can be valid, so do not grade by exact agreement with the old tool sequence. [Agent evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Split evaluation by investigation or task family, not neighboring turns from one investigation. Keep planted causes, sealed labels and grader explanations out of available context and policy development. Measure evidence coverage, unsupported claims, useful next decisions, cost and stop behavior; also test on planted-cause and null tasks end to end. Context policy is a major determinant of performance alongside model ability, instruments and available evidence. Recorded turns make those factors independently testable.

### Checkpoint contract

An inference export pins builder source and constructor arguments, preprocessing/tokenizer, weights and persistent buffers, runtime, expected inputs/outputs and tolerances. A resumable training checkpoint additionally captures optimizer slots and parameter mapping, scheduler, mixed-precision scaler, random states per rank/device, sampler and data-stream cursor, component state, completed step and gradient-accumulation position, distributed topology, and checkpoint schema. Prefer checkpointing immediately after a committed optimizer step. Capturing mid-accumulation requires saving accumulated gradients and microbatch position. Save streaming data offsets or declare that the loader cannot resume exactly. Snapshot all shards at a common step and publish the manifest only after every required rank acknowledges. |---|---|
| Exact in a specified environment | Identical builder, environment, logical step, data stream and replayable state. An uninterrupted control and a resumed run pass the declared equality check over test steps and outputs on supported hardware. |
| Numerically equivalent under protocol | Restoring across hardware, parallelism or implementation can change reduction order. Log all differences and verify outputs plus update trajectory under prespecified tolerances; qualify each supported combination. |
| Warm start / migrated model | Record a mapping for each copied or transformed tensor and new or dropped training state. Evaluate the child independently. |
| Inference-only / unrestorable | Record the available bundle and checks, or the dependency that was lost. Show claims and retained evidence with an explicit restoration status. |

## Checkpoint branching and repairability

[[branching]]

**A branch asks what would happen from a particular training state.** A checkpoint is a committed immutable snapshot. Resume continues the same scientific trial under its lock and declared continuity class. A branch creates a child trial with a parent checkpoint, intervention, migration and additional budget. Rewind creates a child from an earlier checkpoint. Training from scratch has a fresh initialization and an independently recorded recipe. These operations expose different scientific questions through the same execution system.

| Branch contract | What must be explicit |
|---|---|
| Parent identity | Checkpoint manifest, originating trial/step, builder and environment, training history and available state. |
| Intervention | Exact component/source digest and config; affected data, weights, structure, loss or update state; requested model mode. |
| State migration | Per-state copy, transformation, reset or omission; stable parameter mapping; optimizer, scheduler, scaler, buffers, RNG, data cursor and component state. Reject undeclared missing state. |
| Randomness and data | Paired or independent stream policy, initialization seed, branch-local stream handles and data offsets. Pairing is a deliberate design choice. |
| Compute | Additional examples/steps/device time, stopping rule, inherited training cost and total discovery/confirmation cost. |
| Eligibility | Restore class, qualification fixtures, required parent-isolation checks, allowed deviations and comparison group. |

### Branch admission and isolation

1. Request a snapshot at a supported safe boundary. For a live distributed run, commit all required ranks at one logical step before the parent continues. A partially written checkpoint cannot be a branch parent.
2. Resolve the child lock and migration, reserve its budget and record a branch intent with a durable command key. This uses the normal outbox, workflow, attempt and fencing machinery.
3. Restore into a separate process/address space by default. Mount parent artifacts read-only and assign separate scratch/staging paths. Device allocations and mutable state belong to the child.
4. Validate semantic continuity where promised. Run the relevant no-change restore fixture and an intervention fixture. A disruptive structural change can qualify as an intentional warm start; it must not be mislabeled exact continuation.
5. Publish the child manifest and typed lineage through the fenced commit API. Check complete shard sets and inherited identities. A failed child cannot modify or publish over the parent.

**In-memory optimizations need a stronger qualification.** A Python `state_dict()` is not an isolated checkpoint. In our local PyTorch check, loading Adam state directly into another optimizer shared moment tensors, so subsequent child steps could change the parent optimizer. Clone mutable state through a qualified path and verify storage independence. Include Python, NumPy, torch CPU/device and custom generators, mutable buffers, model mode, data state and component-owned state where applicable. Check parent fingerprints and behavior at a stable boundary before/after a child mutation. A concurrently training parent's bytes naturally change, so compare against the committed snapshot or an uninterrupted matched control. At scale, process isolation and immutable manifests enforce the boundary; exhaustive hashing of multi-terabyte live state on every branch is not the default.

### A reusable repairability study

Install a planning component that expands checkpoint times × interventions × added budgets × independent training seeds. Columns can include an immediate weight edit, changed data, a head reset, a new update rule and an architecture graft. Include no-change continuation and the controls needed by the specific question. Add from-scratch arms when making a recipe or architecture claim. A local checkpoint-repair claim can remain narrower.

Cells report the behavior reached within the stated additional budget, guardrails, uncertainty and restoration class. Failed, incomplete and missing cells are distinct. Repeated branches from one parent share training history; they are not independent replications. Pair arms within parent trajectories and report variation over independently trained parents, with example-level uncertainty at the appropriate grouping unit. Reuse outputs only when input identity, measurement contract and necessary execution conditions agree.

Choose checkpoint retention according to expected information value and storage cost. Start with coarse times and a few justified interventions; refine promising regions. A failed repair means “not achieved by this intervention within this budget.” Test longer budgets when that would distinguish slow recovery from apparent loss of plasticity. A search-selected stopping time and intervention require a separate frozen evaluation before becoming an automatic policy.

## Realized isolation and assessment eligibility

[[isolation]]

**Record the boundary that actually existed.** Every evaluation plan requires a versioned set of capabilities. Every evaluation receipt records the requested profile, selected configuration and observed enforcement evidence. A label such as `os-user+fs-perms+sandbox` is a readable summary, not proof by itself. Profiles are sets of controls and threat assumptions, not a single ordering in which one OS label automatically outranks another. A trusted launcher records probe results and configuration digests; candidate code cannot self-certify the receipt.

| Receipt field | Meaning |
|---|---|
| Required controls | Plan/profile digest; who must be unable to see labels, candidate outputs, secrets and restricted evidence; permitted network/device access and output policy |
| Observed execution | OS/kernel and host identity, launcher release, sandbox/VM configuration digest, credential identities, mounts, process/network policy, resource limits and device grants |
| Verification | Per-control `passed`, `failed` or `unknown`; executed probe-suite digest and results, observation time and evidence handles; independently qualified configuration identity |
| Scope and gaps | Trusted host operator/kernel/driver assumptions, unsupported checks, environment drift and actual deviations; no hardware attestation claim unless one exists |
| Scientific linkage | Frozen plan, candidate builder/checkpoint, input split, trusted scorer, admitted attempt and fence; output and exposure-policy references |

Admission checks whether the selected runner can satisfy the plan before spending its evaluation budget. The assessor then checks the **actual receipt** and required qualification at assessment time. Missing or failed mandatory controls block `protocol-passed`. Record conformance as deviated or incomplete and outcome as inconclusive when eligibility cannot be established. That is not evidence that the model itself failed. A lower-security exploratory plan may be valid on the same machine, but cannot be silently substituted after seeing the result. Changing its requirement is an attributed, exposure-informed plan/charter change as applicable.

**Linux profile.** Use distinct service identities where supported, restrictive filesystem permissions and a versioned bubblewrap sandbox configuration. nsjail is a possible alternative adapter, not a second mandatory sandbox. Restrict process visibility, mounts, network and devices; grant only required accelerator access. A sandbox binary alone is insufficient: bubblewrap explicitly places responsibility on its configuration. Qualification tries unauthorized label/credential reads, host writes, child-process escape paths and network exfiltration, and verifies permitted computation still works. Record which checks passed for this exact profile. Kernel, administrator and accelerator-driver compromise remain outside a declared local-process threat model. [bubblewrap security model](https://github.com/containers/bubblewrap#sandbox-security) · [nsjail capabilities](https://github.com/google/nsjail)

**macOS profiles.** Host-native same-user development is explicitly `dev:same-user`; separate API tokens do not prevent that user from reading files or credentials. It supports exploratory work and debugging. For a sealed evaluation, the local supervisor launches a qualified Linux VM profile through Lima, with separate guest identities and the Linux sandbox inside it. Use no broad home-directory, credential or host-socket mounts; transfer declared inputs through a controlled channel. Disable unintended guest egress and ensure candidate inference cannot reach the trusted scorer's labels or capabilities. Lima's configurable mounts make it a useful VM substrate, not an already-qualified evaluator. VM setup and isolation probes are part of the shipped profile's acceptance. [Lima filesystem configuration](https://lima-vm.io/docs/config/mount/)

**The candidate is untrusted even when it is called a model.** Arbitrary PyTorch code and checkpoint deserialization can execute code. Candidate inference runs in a restricted child with evaluation features only. A separately authorized scorer owns labels and joins bounded predictions by case ID. The scorer never imports candidate code or unpickles a candidate-controlled Python object in its privileged process. Use validated data formats at that boundary. Restrict output channels, logs, access frequency and feedback released to the investigator. Keep sealed labels outside investigator/training grants from dataset registration onward; isolating inference cannot undo earlier exposure.

An assessment worker decides plan conformance and publishes through the command service. The sealed runner measures under restricted access. Those are different roles even on one machine. Neither receives the authoritative database writer role. A local machine owner remains trusted to administer the lab; the design does not claim to hide data from that owner. If an isolation configuration is later found defective, trace affected receipts and append health/assessment corrections through the same dependency graph used for component withdrawal.

## Operations and trust

**Local identity and secrets.** Service principals and scopes exist even in a single-user lab. Give an admitted worker only authorized inputs, scratch space and a staging capability; protected storage APIs enforce those grants. OS/VM profiles enforce process access where required. Loopback binding is not authentication, and process-level tokens are not OS isolation. Keep control services inaccessible to sandboxed candidates. Domain researchers choose data/model-call egress policy. A future hosted deployment adds tenant IAM and stronger cross-tenant isolation without changing the scientific contracts.

**Scheduling, costs and physical resources.** Reserve GPU/time, model tokens or currency and storage as independent dimensions with atomic counters. Reserve the full potential child envelope or a rolling bounded allocation before dispatch; release unused capacity on reconciliation. Count shared provider calls once in the billing ledger and attribute them along the invocation tree for reporting. Track warm-start compute inherited from earlier checkpoints when comparing total research cost. The backend adapts from a local process supervisor to Kubernetes Jobs or a distributed job operator with gang scheduling; Kueue admits workloads under quotas where configured. A trial scheduler chooses *which candidate is worth training*. Kueue chooses *when that requested job may consume cluster resources*. Predictable device budgets also require deadlines enforced on the worker, since provider charge updates may arrive late. [Kueue workload lifecycle](https://kueue.sigs.k8s.io/docs/concepts/workload/) · [Kueue controller](https://github.com/kubernetes-sigs/kueue/blob/da56e24d1be4a9d1f91c63f2e28972789adcab44/pkg/controller/core/workload_controller.go) · [Tune research platform paper](https://arxiv.org/abs/1807.05118)

The project reserves a configurable confirmation envelope so exploration cannot spend it accidentally. A revised envelope is an attributed policy change. Charge branch ancestry once in aggregate accounting and show inherited cost for each comparison. Infrastructure retries remain actual costs even when the scientific comparison excludes them. Assessment, controls, monitoring evaluation and investigator calls all consume the declared research budget.

**Throughput and retention.** Keep per-step tensors and telemetry off the control database. Batch metrics into columnar shards, retain summaries and selected exemplars, and index their locations. Local disk space, memory and device occupancy are admission resources. Prioritize checkpoints and essential evidence over optional traces when storage is pressured. Pin exported models and evidence cited by retained claims, apply project retention/deletion policy, and expose how deletion affects replay. The lab must remain responsive while training saturates its allowed resources; reserve capacity for control services. Concurrency is configured from measured machine capacity, not a fixed cluster-size assumption.

**Operations and upgrades.** Correlate command → turn/workflow → trial → attempt → backend ID → artifact manifest in structured logs. Monitor stale leases, unknown cost, orphan bytes, disk pressure, evaluation access and evidence visibility. `lab backup` records a consistent ledger snapshot and referenced blob inventory, Temporal persistence, service versions and encrypted credential material or documented re-enrollment requirements. The backup coordinator quiesces new admissions/publications and orchestration changes to obtain a compatible watermark; running jobs follow an explicit checkpoint/pause policy. Verify referenced bytes before declaring backup success. `lab restore` validates that bundle and reconciles external processes before enabling scheduling. Test both graceful backup/restore and recovery from an unclean shutdown. A service rollback must remain schema/history compatible; selecting an older scientific method affects new bindings and never rewrites history.

**Local release targets.** Publish a reference-machine and workload definition before performance testing. Measure installation/startup overhead, idle memory, command latency while training, evidence visibility, backup/restore and disk-pressure behavior. Proposed responsiveness targets are p95 command acceptance within two seconds for already-resolved requests and evidence visibility within 30 seconds of publication, under that declared local load. Run a multi-day investigation with forced turn rollover, service restart and an upgrade. Demonstrate no duplicate logical admission, no accepted stale-epoch publication, no undisclosed state loss and no unauthorized access within each qualified profile's threat model. Backup frequency determines the disclosed loss window; a single local machine does not offer high availability. These are acceptance requirements, not measured results.

## Complete local v1 and scientific acceptance

**Build the complete local product.** The implementation target includes internal LLM investigation, component authoring/reuse, custom PyTorch execution, charter enforcement, qualified planning/assessment, durable bounded turns, checkpoint branching, MCP, CLI/reports, local installation, permissions, upgrades and recovery. Work through implementation dependencies continuously. The table below defines release acceptance for that complete product; it is not a staged roadmap, time box or set of automatic stopping points.

The hosted development agent can build and test the repository, but completion requires a fresh user installation and the acceptance journey on the declared local OS/device profiles. Maintain durable build notes, automated checks and reproducible packaging so development survives session interruptions. Qualify every advertised provider/client/execution profile; unavailable hardware or failed checks remain explicit incomplete release criteria. A full TUI/web app, hosted multitenancy, cluster scheduling and every distributed topology are outside the local v1 release contract. Their adapter boundaries remain designed, and adding them must preserve the same scientific rules.

**How to test the product objective.** Use four arms with the same underlying LLM, PyTorch code, data, tools and total resource envelope: a coding agent with a clear research brief; that agent with our component library and methodology but no dedicated service; the agent operating the service through MCP; and the service's internal investigator. Give the arms comparable setup/tuning effort on separate development tasks. Include unfamiliar custom projects, real failures, verified planted faults and cases with no demonstrated improvement. Planted-cause diagnosis and open-ended architecture discovery are separate tasks; each needs its own success criteria.

The first two arms need no service and can be measured alongside the full build. This is parallel product research, not a milestone that reduces the requested implementation scope. Freeze benchmark charters, practical effect margins, budgets, replication and grader qualification before inspecting comparative results. Include setup effort and its amortization, all investigator/specialist calls, training, controls and recovery costs. Report scientific benefit separately from operational reliability; a platform can improve handoffs without making a better scientific decision. Preserve that distinction when deciding what earns its complexity.

Independent evaluators measure confirmed useful improvements, unsupported claims, time/cost to a useful decision, interruption recovery and reuse on a second project. Track raw claims alongside abstentions so an operator cannot win by asserting nothing. Report results across budgets, with uncertainty over independent tasks and runs. A small pilot can reveal gross failures or useful instruments; a statistically inconclusive difference does not establish equivalence. Prespecify practical margins and replication needs before deciding that a library suffices or that one investigator strategy is superior.

A separate architecture-search comparison includes appropriately tuned existing methods, random search and fresh-initialization confirmation when the claim concerns a new architecture or recipe. A function-preserving reparameterization is not automatically a neutral training placebo: it can change optimization. Validate any null intervention under the relevant training and measurement conditions. If a sufficiently informative comparison shows the library arm matches scientific outcomes, handoffs and reuse at comparable cost, simplify deployment and retain the useful capabilities. Poor performance across operators should prompt investigation of the instruments and task identifiability as well as orchestration.
