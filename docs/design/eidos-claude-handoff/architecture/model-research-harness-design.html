Deployment and ownership

A researcher brings a PyTorch project, a question about a capability, and a budget. The lab should return the strongest answer the evidence supports, a model they can load if one improved, and a recipe another researcher can challenge. “This architecture cannot represent the distinction” and “this one learned it but its readout hid it” lead to very different experiments.

Final architecture baseline · local v1 · Revision 4 · 7 November 2026. Build the complete harness for a researcher to install and use on their own machine. Its internal LLM runs bounded decision turns; durable coordination and scientific records outlive those turns. Components remain replaceable, checkpoint changes create explicit branches, and assessment checks actual execution and isolation against the frozen plan. CLI, MCP and generated HTML reports are the v1 interfaces. This is the implementation baseline, with release acceptance criteria rather than milestone-sized products. The hosted cloud agent session is where we may build the software; it is not a runtime requirement for its users.

All nine architecture diagrams can be enlarged in this document or downloaded as standalone SVG files. The local v1 topology and editable specification are also available separately.

Architecture decision. Build a Python application with an explicit domain core, one command service, independently supervised workers and a small worker SDK. Use local PostgreSQL for research records and accounting, a content-addressed local artifact directory, Temporal for durable coordination, and per-project environments for ordinary PyTorch code. The command API, resolver, catalog and authorized evidence reader ship together. The investigator, training runner, assessor and sealed evaluation runner are separate entry points with separate credentials. Security isolation is an additional, measured property of the selected execution profile. A local supervisor owns startup, health, persistence, logs and recovery. No cloud account, OCI registry, MinIO, Kubernetes or Kueue is required for local v1.

In this design a trial is one controlled test, an attempt is one execution of that test, and a checkpoint is a saved model or training state. A turn is one bounded opportunity for the investigator to inspect evidence and choose actions. A release identifies immutable component code and its contract. A project environment lock describes dependencies; it does not make the code secure. The diagrams use these names consistently.

One logical write path. Planners submit drafts, assessors submit results, and workers submit output manifests to the command service's authenticated command/commit API. They have no direct ledger write credentials. The service checks identity, expected revision, command uniqueness, policy and applicable attempt fencing before atomically committing records and outbox events. Read services use authorized projections. Uploading immutable bytes to a staging prefix is separate from publishing authoritative artifact/evidence records. Neither a planner nor an assessor can bypass this boundary by being an internal service.

The default lab runs CPU work or uses the researcher's available accelerators through a capability-reporting local adapter. A single machine can complete the entire investigation, including independently authorized assessment. Plans requiring sealed execution use a qualified local Linux sandbox or local Linux VM profile. An unavailable device, isolation capability or exact-resume guarantee is reported before dispatch. Remote Linux GPUs and distributed backends remain compatible extensions; the local acceptance journey does not depend on renting a server.

Local product and technology stack

The finished user journey. Install the lab, run lab init and lab doctor, register an existing project and interpreter, choose a local or hosted model endpoint, and start the supervisor. The researcher commits a study charter and launches an investigation through the CLI or MCP. The internal investigator can reproduce a failure, install a new diagnostic, generate data, change a learning rule, branch a checkpoint and propose a structure. The researcher can inspect receipts and plots, steer the investigation, take over, or disconnect while admitted work continues. They finish with a loadable model when justified, a reproducible recipe, and a report that includes negative results and limitations. They can reuse their new component on another project without rebuilding the lab.

CLI names here are proposed product commands, not installed commands in this workspace. lab status --json, lab logs, lab report, lab component validate/publish/bind, lab checkpoint branch, lab backup and lab restore are required surfaces. lab stop has an explicit running-job policy: drain, checkpoint-and-stop where supported, or cancel. Closing an MCP client only detaches that client. A terminal UI may later consume the same queries; neither Textual nor a browser application is required to operate v1. HTML reports supply plots, comparisons, lineage and linked evidence that are awkward to read in a terminal.

Managed local infrastructure. The installer provisions pinned binaries or uses explicitly selected existing services. The supervisor manages PostgreSQL, Temporal, the API and worker processes as one local installation. Use separate PostgreSQL databases/roles for the research ledger and Temporal persistence/visibility; a shared PostgreSQL process does not grant cross-database authority. Bind services to protected local interfaces and authenticate local callers. Start without an Elasticsearch dependency or a separate Temporal web UI. Capture service versions, configuration and health in lab doctor output.

One change from the earlier one-machine suggestion is deliberate: the shipped product uses the regular Temporal Server, not start-dev. Temporal documents start-dev as a development server that omits security checks; its default state is also ephemeral. A persistent --db-filename is useful for development and tests, but does not turn it into the production runtime. Temporal supports running its server binaries directly. Package a qualified single-node configuration with PostgreSQL persistence, supervised restart and backups. This is a local reliability commitment, not a high-availability claim. Local data and environments. Keep configuration, credentials, service data, artifact blobs, job scratch and disposable caches in distinct directories under an operator-selected lab data root. The local artifact backend stages to private temporary files, verifies hashes and sizes, durably publishes bytes, then submits the manifest through the command service. Detect symlink escapes and prohibit arbitrary path reads through artifact APIs. No user project needs a server dependency or a mandatory OCI image. A uv environment isolates dependencies; the execution profile separately determines access to files, devices, processes and network. A failed dependency resolution explains the conflict instead of upgrading the researcher's packages silently. uv workspaces · Python virtual environments

Supported local profiles. Qualify macOS and Linux installations end to end. CPU execution is the portable reference. CUDA and MPS availability is discovered and tested for the selected project; exact numerical restore is never inferred from a device name. On macOS, host-native execution supports exploratory CPU/MPS work; the sealed profile uses a qualified local Linux VM and can evaluate on CPU when the model and plan allow it. Do not promise MPS passthrough into the VM. A model requiring a Linux GPU for evaluation needs a compatible Linux machine or optional remote runner, otherwise that plan remains unavailable. Windows/WSL support is a separately qualified profile, not an implicit v1 promise.

Model endpoints may be local or external. The chosen provider receives only authorized context and tool results under the project's data policy. A local install is not automatically an offline investigation when a hosted LLM is selected. Keep provider keys in the operator's secret store and issue scoped broker access to components. A component that creates synthetic data can have its own bounded LLM calls without owning the lab's credentials or unlimited budget.

Codebase boundaries and reuse

Use one repository for coordinated lab packages and release tooling. Organize around responsibilities that change for different reasons: scientific rules, persistence, agent runtime, execution, transports and author-facing contracts. A uv workspace coordinates the lab's own packages; researcher environments are separate projects with their own locks. Avoid a generic plugin framework, global service locator or framework-wide base class as the component contract.

These are ownership boundaries, not a mandate for one separately published distribution per folder. Publish worker-facing packages independently; consolidate server distributions when that reduces release work without violating imports or credentials. Each executable is a thin composition root. A feature follows a discoverable path from schema to command handler to domain rule to adapter and its relevant tests. Root contributor instructions explain those paths, runnable commands and the evidence required for changes; scoped instructions describe actual local constraints. Architecture decisions record a reason, alternatives and reversal conditions. Keep generated code labeled and reproducible.

Enforced dependency rules. Domain code imports neither frameworks nor infrastructure. Adapters depend on application ports; the application does not import a concrete adapter. Worker-facing packages cannot import server, database, Temporal or LLM libraries. CLI and MCP cannot import persistence or bypass commands. Import Linter checks those boundaries in CI. It does not enforce runtime authorization: PostgreSQL roles/grants, scoped API credentials and OS/sandbox policy do that. The command service gets research_writer; projection readers get restricted read access; migration ownership is a distinct maintenance role. Investigator, assessor, workflow and training processes normally have no research-database credentials. Import Linter · PostgreSQL privileges

The worker compatibility promise. lab-wire and lab-worker-sdk use the standard library. lab-pytorch uses only those packages and the project's already-installed PyTorch; it must not pull a different torch/CUDA build or require Pydantic v2. Server boundary models generate versioned JSON Schema. Worker fixtures are checked against those schemas in a separate test environment, and the server validates received messages. A schema major and supported Python range are explicit. Projects outside the importable SDK range can use the documented JSON subprocess protocol and a small project-owned adapter. Dependency-free is not a promise that every historical Python or PyTorch version works.

Reuse decisions grounded in source

Prefer an upstream dependency for a stable primitive, an adapter for an existing research framework, and a documented pattern when importing an entire runtime would impose the wrong ownership model. Pin source revisions when studying behavior. If we copy or fork code, preserve the applicable license and notices, record origin and modifications, add the relevant conformance fixtures and assign responsibility for upstream fixes. The release includes dependency/license inventory. Do not import a repository's internal modules simply because they happen to be reusable today.

The research loop

The study charter precedes exploration. Commit an immutable charter revision before task-specific exploratory trials are admitted. It fixes the target population and comparison, metric identity/direction/denominator, minimum useful effect, permitted regressions, resource limits, and the decision standard, including uncertainty, multiplicity and stopping policy where applicable. Record the observations already known at charter creation, including imported model results. Choosing a candidate during exploration is allowed; choosing its pass/fail bar after seeing its effect is not a prospective success rule.

Evidence plans inherit the charter. Every plan pins the charter revision, digest and success-rule reference. The resolver materializes those rules, and admission rejects a plan or template that overrides them. Sample sizes, seeds and logistics can be resolved before freezing under the charter's predeclared design policy; any choice informed by observed results is retained as exposure metadata. Missing success criteria permit exploratory work only after an exploration-only charter is recorded, and cannot later be portrayed as pre-exploration criteria for that work.

Later changes are exposure-informed. Amending a threshold, guardrail, metric, target, comparator or decision standard creates a new charter revision with the previous values, rationale, author and exposure-event references. Preserve the original rule and assessments. Mark the amendment exposure-informed when relevant results have been seen, including by a human. A new study ID does not erase those exposures. A new plan can test the revised rule on fresh independent data, while continuing to report that the rule was selected after exposure. A newly discovered question outside the charter follows this same route.

The unit of scientific comparison is a trial under a protocol. The study links its charter to dataset/split identities, comparison unit, search budget and baselines. A change to the evaluation contract creates a new comparison group and can rescore retained predictions when eligible. Rescoring old evidence under a new bar remains an exposure-informed analysis.

  1. Import, charter and reproduce. Register the project's model factory, evaluation command and already-known results. Commit the charter before new task-specific exploration. The adapter describes how to load an example, collate a batch, interpret an output, obtain targets, build the model, and save or load its state. Capture a reference batch, include modes such as evaluation versus training, and check output equality to a declared tolerance in a fresh worker. A bare state dictionary triggers a request for builder and preprocessing information. A project offering inference only can still run probes and paired tests.
  2. Locate the failure. Ask for example IDs and per-example scores before choosing a remedy. Candidate explanations include faulty labels, a shortcut, a representation that loses information, an ineffective update, and an evaluator mistake. When appropriate, measure intermediate activations, gradients or update norms at named points on a small fixed batch. Compare the instrumented and uninstrumented behavior and cost. Compute on the worker, return a statistic, a few cases and an artifact handle. Keep activation capture bounded by layers, examples, precision and byte limits.
  3. Generate different ways to learn. A proposal may return a new model builder, an attributed source patch, weights derived from a parent, a new data generator, an optimizer with additional persistent state, or an entire training step. A researcher can supply conditional search spaces and symbolic transforms. For arbitrary Python, the escape hatch is a new source revision and fixture. The investigator can author a new component inside a restricted build job, run its conformance tests, then bind it on a candidate branch.
  4. Qualify before paying for scale. Check shapes, finite outputs and gradients, task-specific invariants, serialization, and the declared parameter, memory or latency envelope. For a causal sequence model include a future-token perturbation test. A failed qualification retains its failure and generated source. Preserve code, seed and parentage for candidates discarded early.
  5. Allocate comparable trials. Run the current best model and a simple or random-search baseline. Pair seeds and data order where meaningful. Select the compute measure appropriate to the question: equal training examples isolates sample efficiency, equal accelerator time tests practical efficiency, and both matter when a new update doubles the work per step. Record actual tokens/examples, optimizer steps, device time, peak memory and quality at matched points. A replaceable policy can prune or promote using development results. Periodically run some early losers to full budget to estimate whether the cheap screen discards late learners.
  6. Confirm and export. Freeze candidate and analysis before final evaluation. A separate evaluator measures prespecified accuracy, failure slices and resource tradeoffs on fresh seeds and held-out cases. Pair comparisons by task unit, report uncertainty and variation across seeds, and state the scope of any improvement. A frontier of quality, latency and memory can be more useful than a single winner. Export builder, preprocessing, weights, inference checks, environment lock and a recipe for the evaluation. Record negative results and the count of candidates tried.

Scientific decision rule. Apply the success criteria inherited from the pre-exploration charter. For device data, split by device or collection site when that matches the deployment question; thousands of events from one device do not provide thousands of independent device-level observations. Keep common validation data available for search and limit how often confirmation outcomes are revealed. If the measured range includes both material benefit and harm, record an inconclusive result and identify the cheapest discriminating next trial. A lead selected using development comparisons earns its final claim on independent confirmation under the recorded charter revision.

Freedom during exploration. Record the purpose of a run before dispatch, including reproduction, measurement development or open search. Hypothesis-driven experiments should record competing predictions and what would change the next decision. A fixed number of rival hypotheses is not an admission requirement. Exploratory observations can guide the next run immediately. Stronger assertions use the evidence-plan process below.

Fair tuning and disclosure. Declare tuning opportunities and budgets for each arm, including prior search that selected the candidate. Choose appropriate hyperparameter spaces for each method and explain differences; identical ranges can disadvantage a different optimizer. Report training efficiency and total research cost separately. Track which development, generator-feedback and monitoring results were disclosed to each operator and when. A human who sees a monitoring score can influence later choices, so that disclosure belongs in the same record as an LLM-visible score. Count adaptive comparisons, but label any numerical estimate of selection inflation with its assumptions. Keep confirmation access bounded under a frozen plan. Fresh samples from one synthetic generator do not test that generator's assumptions. Adaptive holdout reuse · Leaderboard feedback and adaptive selection

Why allow both source edits and structured search? EvoPrompting used language models to mutate architecture code. PyGlove implements reusable rules on compatible symbolic objects; NASLib offers explicit sampling, mutation and query hooks on its graph abstraction. Those are good optional methods for a project able to use them. Li and Talwalkar found competitive random-search baselines in their studied spaces. I would make a baseline and an independently reproducible comparison conditions of a discovery claim. A source difference alone establishes a new candidate revision. A decision the earlier switch experiment actually supports. An ordinary classifier averaged event vectors and scored 98% on the original synthetic traces, yet solved zero opposite-order pairs. Algebra explains why a permutation disappears in the average. A position-weighted average with the same 86 parameters learned a usable order signal. How a new study would run. A researcher brings an event classifier from a second device. The investigator first tests whether the input representation retains fine timing. If a time-preserving probe succeeds while the trained readout fails, try readout/weight intervention and a changed learning signal. If a pair is indistinguishable before readout, propose two structures: a small learned temporal filter and a recurrent update with persistent per-sequence state. Validate masks and state reset at sequence boundaries. Train both against the baseline on matching budgets, include a shuffled-time control, and measure on held-out devices. A positive result advances one candidate to confirmation. Evidence that device-specific features explain the gain sends the investigation back to data or evaluation.

Claims and evidence plans

A finding has a scope and an evidence requirement. “This edit improved this checkpoint,” “this input contributed to its errors,” and “this training recipe usually learns an unused capability” are different assertions. Record them as separate claim revisions. A successful local repair does not silently become a general explanation or an architecture-discovery result.

The evidence planner expands a versioned protocol template into an inspectable plan. The resolver locks executable dependencies; the command service admits its work. An independently authorized protocol assessor checks realized runs against that frozen plan. The researcher owns the scientific assumptions and policy for promoting a finding. An LLM may propose an explanation or draft a protocol, but it cannot grant its own code authority to assess a claim.

Two independent state axes. Assessment outcome is unassessed, protocol-passed, protocol-failed or inconclusive. Evidence health is intact, affected or withdrawn. A third field records execution conformance as conformant, deviated or incomplete. A deviation can force an inconclusive outcome under the plan's rules. A protocol-passed claim whose scoring method is later withdrawn retains its historical assessment alongside unhealthy evidence; the current view must show both. Protocol failure does not establish the opposite claim. A missing artifact can prevent replay without refuting retained measurements.

From a proposed finding to an assessed result

  1. Draft. An operator files a scoped claim and selects a qualified template. The planner takes its success rules from the pinned charter and produces arms and an estimated cost. A draft can have unresolved logistics, but its success bar cannot be chosen from its exploratory results.
  2. Qualify. Check charter compatibility, template applicability, passing planted/null qualification receipts, comparison units, data access, tuning opportunities and component qualification. A proposed causal explanation lists plausible alternatives that its controls would leave unresolved.
  3. Freeze and admit. The command service verifies the inherited charter rules, immutable qualification receipts, current policy and resource reservation, then commits the frozen plan through the single write path. A qualified and approved template can run automatically within project policy. Human authorization alone cannot qualify novel assessment code.
  4. Execute. Temporal coordinates ordinary trials, private checkpoint branches and sealed evaluation. The investigator can inspect permitted progress, while protected outcomes follow the plan's disclosure rules. Pause, cancellation and partial evidence retain explicit status.
  5. Assess. The assessor reads receipts and allowed evidence, verifies charter/plan conformance, runs the qualified analysis and submits an assessment to the command service. The service fences and commits the result. A changed success rule requires an attributed charter amendment; a changed execution/analysis plan preserves the charter relationship and exposure history.
  6. Reuse or revise. Publish the bounded statement, assessment, evidence health and limitations together. A later project can use it as a prior or propose a transfer study. Catalog retrieval also includes exploratory ideas, counterexamples and failed attempts with their status visible.

The assessor checks a protocol; scientific interpretation remains scoped. Built-in templates include improvement under a resource bound, intervention effects on a failure, feature decodability, and transfer to another population. A feature being decodable does not establish that the model uses it. A targeted intervention plus a restoration and specificity control strengthens a mechanistic account but cannot exclude every alternative. Function-preserving tests apply to transformations that promise preservation. A mathematical impossibility argument is reviewed with its assumptions and model semantics; finite empirical failures alone cannot prove impossibility.

For an improvement claim, use the baseline/comparison, minimum useful gain, tolerated regressions and decision standard in the charter. Estimate sample needs at the relevant unit under its design policy and account for uncertainty in a small pilot; observed pilot effects cannot silently lower the required gain. For a mechanism claim, choose controls that test actual competing explanations. A same-size weight edit is one possible control, not a universally equivalent intervention. For a transfer claim, a new sample from the original generator may be insufficient; the new task, generator or population must match the proposed scope.

An executable plan is also a component output

A planning component implements evidence-plan/1: it consumes a typed claim, pinned charter and bounded study view, then returns a draft with inherited success rules, artifact references and unresolved logistical obligations. The command service stores the draft and controls admission. An assessment component implements protocol-assessment/1 and requires the project's assessment grant. The planner's and assessor's releases are pinned separately. Qualification before template or assessor approval

Executed positive and null controls are mandatory. Before any template or assessor release can be approved for scientific assessment, an independent qualification runner must show that the applicable pipeline detects a known planted effect and stays silent on a known null case. For a template, exercise plan expansion through execution and assessment, so a correct-looking plan cannot pass while producing invalid conclusions. For an assessor, provide controlled evidence/receipt inputs and verify the expected decisions. Test the intended template/assessor pairing as well as each release's contract.

The control suite fixes planted effects, null conditions, expected outputs, repetition counts and acceptance criteria before the qualification run. A deterministic positive must detect its planted effect and a deterministic null must not assert one. For stochastic procedures, require the prespecified detection power and false-positive bounds across repeated controls, reporting uncertainty; one lucky positive and one quiet null are insufficient. Include relevant grouping, noise, missing-data and invalid-receipt cases for the approved scope. A mismatched or incomplete qualification produces a failed or inconclusive gate, never approval.

Store immutable qualification receipts linked to exact code, dependencies, control-suite and environment identities. The command service's promotion handler checks these receipts before accepting an authorized approval. A human signature cannot bypass the gate. New or changed templates/assessors must qualify for their requested scope; an unqualified method may remain project-local and exploratory but cannot issue authoritative protocol-passed assessments. If controls cannot yet be constructed, qualification is unfinished and promotion remains unavailable. Existing approvals are suspended for affected uses when supporting controls or releases are withdrawn.

Independent authority and honest evaluation. The assessor uses project-approved code in a distinct execution identity. Candidate inference remains isolated from labels and trusted scoring. Assessment plugins run in restricted workers with the minimum grants, never as arbitrary code loaded into the command service. If an open-ended task requires a model or human judge, version the rubric, measure judge reliability on relevant controls and include that uncertainty. Model-generated observations can support an appropriately validated measurement; fluent self-approval cannot substitute for qualification.

Exposure and support are durable records. Development feedback may guide search. Generator-feedback data may guide data creation; record any overlap with selection data and choose separate sets when the question requires independence. Monitoring results disclosed to humans count as feedback if they can influence the investigation. Confirmation results released repeatedly need an explicit reuse policy. Do not infer a universal overfitting penalty from a comparison count alone. Adaptive data analysis

When a defect is reported, traverse typed support dependencies and apply the affected-condition predicate. Mark affected assessments for reassessment and queue eligible rescoring with estimated cost. Replaying identical outputs can establish equality for those retained inputs only; it cannot prove global semantic equivalence or repair a flawed assumption. An unaffected sufficient justification can keep a claim supported. Unsupported means its current support is inadequate, and does not mean the statement is false.

The component contract

A component is a versioned executable research capability that declares what it needs, what it can change, what it produces, and how its behavior can be checked. A release bundle can carry several exported components. A capability is the semantic contract, including input and output meaning; a component release implements it. A run is one invocation of a resolved release. An artifact is data produced or consumed by a run. A claim is a scoped statement, an evidence plan specifies how it will be assessed, and an assessment records what that plan established. These identities have different lifetimes.

Inside a researcher’s model adapter

Start with the author’s existing build(config) and predict(model, batch). An adapter names immutable fixtures and the model-input and output contracts. Author, install, replace, remove

  1. A human or external agent authors components in a project workspace, runs the local contract suite, then submits an immutable source bundle through the same publishing route. A remote MCP host exchanges an upload grant or a registry digest; a laptop path alone has no meaning on the worker.
  2. A builder resolves dependencies in a separate project environment, runs tests, records source/environment digests and its achieved isolation, and publishes through the command service. Dependency isolation alone is not a sandbox. Validation includes negative fixtures, deterministic checks where promised, bounds, and a restore fixture for stateful methods. Installation exposes metadata for discovery. Enabling it changes a specific project profile revision. Package installation and build scripts are code execution and receive the selected execution profile's restrictions.
  3. Before a run, resolve all required providers and artifacts, verify grants, materialize an execution lock, and reserve budget. On a long investigation, the next decision can discover a newly enabled scorer and apply it to old predictions. An in-flight trial continues under its pinned lock.
  4. Replacing a default affects subsequent resolutions. To change a running trial at step 8,000, save a checkpoint and fork from it. The migration declares which states are copied, transformed, initialized or dropped. Run fixture comparisons and record lineage before promoting a child. If compatible resume fails, offer an explicit warm start or fresh training.
  5. Retirement hides a release from new profile bindings. Retain blobs needed by live jobs, exported models and retained evidence. Replacing or retiring a sound release does not invalidate its historical results. A scientific withdrawal names the defect, affected releases, conditions and evidence dependencies. A metric bug can require rescoring; a training-rule defect may require new training. Append corrections and reassess affected support without overwriting history. A claim with another sufficient, unaffected justification can retain support.
  6. Purging restricted or revoked code is an explicit operation with affected dependents, execution restrictions and tombstones. Mark a historical model unrestorable if indispensable code was purged; that alone does not make its retained observations false. A security revocation can stop jobs immediately under policy. A scientific defect pauses or quarantines only affected work at an appropriate boundary. Material changes to running scientific behavior create a branch.

Bounded investigator turns and recovery

Long investigation; short agent runs. A durable investigation coordinator schedules a bounded child workflow for each decision turn. The child runs model and tool work as activities and ends after its action/call/time/token limits or a durable wait condition. It does not remain alive through a three-day training job. Admitted jobs have independent durable identities and lifetimes; their completion wakes the coordinator for another turn. A specialist component may use the same bounded pattern, charged to its parent budget. No essential investigation state exists only in an agent object, Python kernel or conversational summary.

Before starting a turn, the command service commits a TurnSpec. The context builder reads the authorized ledger and artifact views at that specification's horizon. The investigator may make several model calls within the bounded turn, recording each accepted decision and its tool-call ordering before executing effects. Completion stores the turn result through the same command API. The next turn reconstructs context from evidence, pending jobs and steering, including newly enabled components. An existing trial retains its old lock. Installing a method is not permission to replace scientific code mid-run.

import hashlib
import json

def command_key(project_id, turn_id, decision_id, call_index, subcommand_index=0):
    identity = ["lab-command/1", project_id, turn_id, decision_id,
                call_index, subcommand_index]
    return hashlib.sha256(json.dumps(identity, separators=(",", ":")).encode()).hexdigest()

The indices come from the persisted accepted decision, never an in-memory counter or parallel completion order. A retry loads that decision and resubmits the same key and arguments. If a lost model response must be regenerated before any decision was accepted, it gets a new decision identity; the old unaccepted response had no authority to execute tools. Resume continues the same scientific trial under its lock and declared continuity class. A branch creates a child trial with a parent checkpoint, intervention, migration and additional budget. Rewind creates a child from an earlier checkpoint. Training from scratch has a fresh initialization and an independently recorded recipe. Branch admission and isolation

  1. Request a snapshot at a supported safe boundary. For a live distributed run, commit all required ranks at one logical step before the parent continues. A partially written checkpoint cannot be a branch parent.
  2. Resolve the child lock and migration, reserve its budget and record a branch intent with a durable command key. This uses the normal outbox, workflow, attempt and fencing machinery.
  3. Restore into a separate process/address space by default. Mount parent artifacts read-only and assign separate scratch/staging paths. Device allocations and mutable state belong to the child.
  4. Validate semantic continuity where promised. Run the relevant no-change restore fixture and an intervention fixture. A disruptive structural change can qualify as an intentional warm start; it must not be mislabeled exact continuation.
  5. Publish the child manifest and typed lineage through the fenced commit API. Check complete shard sets and inherited identities. A failed child cannot modify or publish over the parent.

In-memory optimizations need a stronger qualification. A Python state_dict() is not an isolated checkpoint. Clone mutable state through a qualified path and verify storage independence. Include Python, NumPy, torch CPU/device and custom generators, mutable buffers, model mode, data state and component-owned state where applicable. Check parent fingerprints and behavior at a stable boundary before/after a child mutation. How to test the product objective. Use four arms with the same underlying LLM, PyTorch code, data, tools and total resource envelope: a coding agent with a clear research brief; that agent with our component library and methodology but no dedicated service; the agent operating the service through MCP; and the service's internal investigator. Give the arms comparable setup/tuning effort on separate development tasks. Include unfamiliar custom projects, real failures, verified planted faults and cases with no demonstrated improvement. Planted-cause diagnosis and open-ended architecture discovery are separate tasks; each needs its own success criteria.

The first two arms need no service and can be measured alongside the full build. This is parallel product research, not a milestone that reduces the requested implementation scope. Freeze benchmark charters, practical effect margins, budgets, replication and grader qualification before inspecting comparative results. Include setup effort and its amortization, all investigator/specialist calls, training, controls and recovery costs. Report scientific benefit separately from operational reliability; a platform can improve handoffs without making a better scientific decision. Preserve that distinction when deciding what earns its complexity.

Independent evaluators measure confirmed useful improvements, unsupported claims, time/cost to a useful decision, interruption recovery and reuse on a second project. Track raw claims alongside abstentions so an operator cannot win by asserting nothing. Report results across budgets, with uncertainty over independent tasks and runs. A small pilot can reveal gross failures or useful instruments; a statistically inconclusive difference does not establish equivalence. Prespecify practical margins and replication needs before deciding that a library suffices or that one investigator strategy is superior.

A separate architecture-search comparison includes appropriately tuned existing methods, random search and fresh-initialization confirmation when the claim concerns a new architecture or recipe. A function-preserving reparameterization is not automatically a neutral training placebo: it can change optimization. Validate any null intervention under the relevant training and measurement conditions. If a sufficiently informative comparison shows the library arm matches scientific outcomes, handoffs and reuse at comparable cost, simplify deployment and retain the useful capabilities. Poor performance across operators should prompt investigation of the instruments and task identifiability as well as orchestration.
