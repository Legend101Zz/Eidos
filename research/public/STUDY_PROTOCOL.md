# Eidos research study charter — draft 0.3

Prepared 7 November 2026. **Exploratory preparation only. No comparative experiment has been run, no confirmatory protocol is frozen, and no external preregistration exists.** This document is independent of the implementation campaign. Its $200 allocation is not a research budget.

## Question and scope

Does the same underlying LLM, operating through Eidos, achieve more independently verified improvements on unfamiliar PyTorch projects under comparable resource envelopes than an equipped coding agent? Superiority, autonomy and novelty remain hypotheses. The target population is the selected, eligible project families and resource tier, not all ML research. Familiar public benchmarks test competent execution under disclosed exposure; private transfer projects test limited transfer. Neither establishes absence of pretraining contamination.

## Four controlled arms

| Arm | Intervention |
|---|---|
| 1 | Coding agent, research brief, ordinary shell/editor/Python/search tools |
| 2 | Same coding agent plus the frozen component library and written research method, callable directly without Eidos |
| 3 | Same external coding agent operating Eidos through MCP, with the same library and method |
| 4 | Eidos internal investigator, same underlying LLM, same library and method |

The primary contrast is 4 minus 2. Secondary contrasts 2−1, 3−2 and 4−3 estimate method/library, service-access and investigator-policy effects in this configuration. They are not a complete factorial decomposition and interactions are possible. Freeze the external agent scaffold, prompts, provider settings, context limits and all Eidos/component versions. Give all arms equal task information, dataset access and permitted intervention classes. Arm 2 receives callable equivalents for every public scientific component supplied to arms 3/4. Infrastructure conveniences are the intended difference. Do not cripple baseline tools to force ledger-like behavior.

Include pinned AIDE as an additional published-agent comparator on a prospectively selected compatible code-to-metric subset. Configure its code, feedback and report LLMs explicitly; defaults can use different models. Count all stages and retries. Its search metrics are not the independent final grade. Report subset results separately; AIDE does not replace any controlled arm.

## Outcomes and proposed practical decision

Primary endpoint: family-balanced probability of an independently verified, useful improvement within budget on eligible improvement projects. A run succeeds only if its locked candidate beats the supplied functioning baseline by the task's prespecified practical gain, meets all guardrails, reproduces independently and satisfies the declared claim scope. Exact task gains depend on domain utility and development qualification, and must be fixed before the comparative exploration they govern. A planted diagnosis result and an operational recovery result do not count as model improvement merely because they pass a test.

**User-adopted practical standard (7 November 2026, before comparative outcomes):** a minimum useful arm-4 minus arm-2 gain of **10 percentage points**, meaning one additional verified success per ten research attempts at the same envelope. For a claim that the advantage exceeds this useful margin, require the lower end of a two-sided 95% confidence interval to exceed +0.10. A lower bound above zero but not +0.10 supports a narrower advantage claim, not the proposed practical claim. A point estimate above +0.10 with uncertainty spanning zero is inconclusive. The user approved this practical standard in the continuing research session. This approves the decision rule, not a research campaign budget or a claim that the planned sample is adequately powered.

For task-specific practical bars, proposed starting values are +2 absolute percentage points for classification accuracy, a 5% relative reduction in RMSE/MAE, and a 10% runtime reduction for optimization tasks while preserving their fixed quality target. Require no more than a 0.5-point accuracy regression on prespecified critical classification slices; domain-specific guardrails can be stricter. These are draft defaults for domain review, not agreed thresholds, universal utility judgments or the already fixed reference-qualification bars. This paragraph was added after reference qualification but before any comparative system outcomes. Record that exposure when adopting or changing a task bar; confirm on eligible independent data. Final uncertainty rules apply to the task's chosen gain/guardrails, not just the point estimate.

Report separately: continuous improvement over baseline in native units; valid reproducible candidate rate; unsupported causal/architecture claims; calibrated abstention; diagnosis accuracy on planted cases; recovery/branch integrity; transfer performance; time to first verified candidate; and total cost. Do not collapse scientific benefit and operational reliability into an arbitrary composite. A no-improvement/null task is in the abstention/false-claim stratum, not a free primary success. No improvement found does not establish impossibility.

Task-level confirmation is paired where valid. Classification improvement uses paired predictions and case/group resampling; time series uses independent series/subjects or blocks, never arbitrary timepoints as independent projects. For recipe/architecture claims, confirmation includes fresh training initializations with equal training and tuning allowances. A repaired inherited checkpoint supports only a checkpoint-specific result unless fresh runs corroborate it. Successful alternative methods receive equal credit; references are existence demonstrations, not required answer strings.

## Budget and repetition recommendations — not authorized campaign limits

Local qualification uses existing CPU resources, no paid LLM calls and no rented GPUs. Development execution limits are fixture-specific and published. Preparation cost does not estimate autonomous-agent cost.

Proposed development comparative pilot, only after a separate authorization: 14 capability cards across eight correlated project clusters and multiple model/data families, 3 independent investigator runs per eligible arm/card, stratified 30-minute and 2-hour research envelopes after timing qualification. Cards sharing a project are correlated and do not create new independent tasks. Keep development feedback open and label it as such.

For planning a final study, consider 40 distinct projects across at least 8 project families, 3 independent investigator runs per arm/project (480 four-arm runs), with a separate AIDE subset. This is a feasibility/precision starting point, not a powered confirmatory sample. Choose family count before adding repeat seeds; repeats estimate stochasticity but do not replace projects. The currently prepared candidate inventory is smaller and is not the promised final sample.

A simple paired binary approximation illustrates the problem: with discordance q=0.40 and true difference d=0.20, detecting d>0.10 with 80% power at a two-sided 5% threshold needs roughly (1.96+0.84)^2*(q−d^2)/(d−0.10)^2 ≈ 283 independent pairs before clustering. Detecting d>0 with d=0.10 and q=0.40 needs about 306. At 40 independent pairs and q=0.40, the approximate 95% half-width is 0.20. These are sensitivity calculations, not a forecast from observed Eidos effects. Family correlation and heterogeneous budgets can worsen precision. After openly labeled pilots, simulate the planned family/task/run hierarchy over a prespecified range of rates and correlations; set count from precision and affordable cost. Do not shrink the margin to fit a favorable pilot. If resources support only an estimation study, call it that.

Use a multidimensional envelope: elapsed time, model input/output/reasoning tokens or billed spend, CPU-core seconds, accelerator type/device seconds, peak memory, disk, network and concurrent jobs. Freeze whether stopping occurs at the first exhausted limit (recommended). Report setup/tuning labor and machine cost separately and amortized at 1, 10 and 100 projects; show all totals, including failed proposals, specialists, synthetic-data generation, training, validation, final confirmation and recovery. Equal dollars alone do not equalize training opportunities. Research and independent confirmation each receive equal reserved ceilings across arms, both counted. Never let an arm use hidden confirmation as an extra search oracle.

## Allocation, analysis and missing outcomes

Pair task/start-state and prespecified research envelope across arms. Randomize/interleave arm order within project/run/time blocks. Pin provider snapshot where available and log returned model identifiers; freeze decoding, reasoning and context policies. If a provider changes, suspend the affected block and prospectively replace/re-run all arms in that block under one version, preserving old observations and costs. Unpinnable providers limit causal interpretation. Reset memory between tasks except in a separately declared transfer sequence with identical source information for every arm.

Compute a per-task success proportion over independent investigator runs; average tasks equally within family, then families equally, and take paired contrasts. Preserve paired arms while resampling family → task → run blocks. Report every family's estimate, repeat variance, raw denominators and an overall hierarchical bootstrap interval; with few families treat intervals as exploratory and add leave-one-family-out sensitivity. Freeze the exact analysis implementation, bootstrap seed/count and small-cluster alternative before final runs. Primary 4−2 is one test; use Holm correction for the three secondary controlled contrasts if making inferential claims. Additional strata/metrics are descriptive unless separately registered with a multiplicity rule. No optional stopping based on favorable effects.

All assigned runs stay in the intention-to-evaluate denominator. Agent-caused invalid, timeout, budget-exhausted or absent outputs yield no verified success, with reasons separately counted. A common infrastructure incident may trigger a blinded replacement of the whole paired block under a prespecified rule; retain incident records and costs. A task/grader defect causes blinded all-arm quarantine, not selective deletion; report bounds with quarantined outcomes and an amended analysis. Unknown cost is unknown, never zero. No rerolling an unlucky agent seed. User cancellation or unscheduled provider outage remains explicit. Do not present best-of-n as a single-run success.

## Charter, exposure and freeze sequence

The archived draft 0.1 preceded new qualification execution in this workspace. Draft 0.2 incorporates the openly labeled qualification results and the 14-card/eight-cluster development design; it is exposure-informed for those references. No four-arm outcomes have been observed. Already known: the public switch-order and image worked examples, branching checks, architecture narrative, source task definitions and published benchmark results. Those examples are development only. The arm-level +10-point/95%-interval standard was approved on 7 November 2026 after local fixture qualification and before any comparative outcome. Task-specific gains remain proposals.

1. Preserve the approved practical margin in this charter revision; record the exact shared provider/model and compute envelope in a subsequent revision before comparative exploration.
2. Qualify tasks/graders and estimate costs on openly marked development pilots. Retain all failures and threshold amendments with the exact exposure history. A changed bar is prospective only for later eligible comparisons; a new study ID does not erase exposure.
3. Lock selection rules before comparing Eidos on the final suite. Select by eligibility, family quotas and a committed randomized procedure, never observed arm advantage. Freeze tasks, data splits, candidate interfaces, rubric, budgets, repetitions, systems, analysis and exclusion rules. Independent grader qualification and actual access isolation are admission gates.
4. Run one final round with frozen systems and no adaptive feedback. Any evaluation information used for a fix becomes development evidence for the next version. If future rounds A/B are chosen, keep v1 frozen and run v1 and v2 together on B; never infer a version gain from v1-on-A versus v2-on-B.
5. Release outcomes only under the agreed disclosure policy. A local hash is an integrity commitment, not proof of date or an external preregistration.

## Source-based design decisions and preparation update

[AIRS-Bench](https://arxiv.org/abs/2602.06855) supplies diverse research tasks and separate agent/evaluator data preparation; its published GPU envelope is not reproduced by our CPU fixtures. [MLGym](https://arxiv.org/abs/2502.14499) supplies open-ended tasks and an agent/environment separation. Its repository is archived at inspection. [Speedrunning](https://arxiv.org/abs/2506.22419) distinguishes hinted reproduction from open-ended optimization; its native eight-GPU setup is deferred. [AIDE](https://arxiv.org/abs/2502.13138) is a useful tree-search baseline on compatible tasks; its own reported metric is not a trusted final grade. [RE-Bench](https://arxiv.org/abs/2411.15114) motivates reporting budget curves and repeated-run variation, while its deprecated tasks and protection requests make it background only here. See pinned code and licenses in `development/NOTICES.md`.

Qualification now covers 14 development cards, 27 numerical reference cases, three lifecycle seeds, four narrow upstream metric fixtures and a separate five-project private candidate pool. These are executed sufficient methods and engineering controls, not an autonomous investigation or comparative study. A private null control has construction overlap with development and is excluded from unfamiliar-transfer and primary-improvement claims. Exact private identities and dispositions remain outside this export. The final sample size, family quotas, practical task bars and common resource envelopes remain unresolved.

`development/analyze_results.py` implements the draft paired family/task/run estimator with an explicit assignment roster and zero verified success for missing assigned outputs. Analytically known synthetic controls cover family weighting, all-zero/all-one contrasts and missingness. It has not been calibrated for coverage under the intended final hierarchy, and does not implement the separate human adjudication or complete cost audit. Freeze a reviewed analysis implementation and validate interval coverage/power before confirmatory use.

## Synthetic interval stress check — before comparative runs

A bounded calibration used 400 synthetic datasets per scenario, 799 bootstrap draws and seed 71107026 across eight balanced designs (four tasks/family, three runs/task). It probes an independent vectorized implementation of the same paired hierarchical percentile-bootstrap algorithm; two datasets were compared with the actual analysis function. It is not exhaustive software validation or a campaign power calculation. The target is the random-family population contrast; conditioning on sampled families gives a different estimand.

In a moderate correlated binary model at a true +.20 contrast, nominal 95% population coverage was 85.3% with three families (Monte Carlo 95% interval 81.4–88.4%) and 93.5% with eight (90.6–95.5%). Extreme perfectly correlated family scenarios were worse. These constructed scenarios are not predictions of Eidos effects, but they refute treating the current percentile interval as automatically calibrated with few families. More seeds within a family do not repair missing family diversity.

**Admission gate:** the approved practical decision rule stays unchanged. Before confirmatory use, freeze whether inference targets the fixed selected task set or a random-family population; choose and independently calibrate the interval method and sample design over plausible dependence/heterogeneity. Do not declare superiority from this draft bootstrap merely because its lower endpoint exceeds .10. If resources cannot support defensible inference, report estimation/exploration and no practical superiority decision. Full calibration source and uncertainty are in `development/qualification/interval-calibration.json`; reproduce with `python development/qualification/calibrate_intervals.py --out /tmp/eidos-calibration.json` from the public root.
